## 3. 대출 심사: 관리자 승인 방식

**문제**: README는 조건 기반 "자동 승인/거절", extend 문서는 "관리자 심사"로 방식이 달랐습니다.

**수정**: README 5-1장에 **대출 심사 프로세스**를 새로 추가했습니다.

```
[회원] 대출 신청 (재직상태, 월소득, 희망금액, 기간, 상환방식, 입금받을 계좌)
   ↓  상태 = 신청(APPLIED)
[관리자] 신청 내역 확인 (시스템은 참고 지표만 표시)
   ├─ 거절 → 거절(REJECTED), 거절 사유 필수 → 회원 알림
   └─ 승인 → 한 트랜잭션으로 대출금 입금 + 상환 스케줄 생성
            → 상환중(ACTIVE) → 전 회차 상환 시 상환완료(CLOSED)
```

- 대출 상태: `APPLIED → APPROVED → ACTIVE → CLOSED`, 또는 `REJECTED`, `CANCELED`(심사 전 회원 취소)
- `LOAN` 테이블에 **입금계좌FK, 심사관리자FK, 심사일시, 거절사유** 등의 컬럼을 추가했습니다.
- 업무 분담: **팀원3**이 승인/거절 로직(`LoanService.approve()/reject()`)을 만들고, **팀원4**가 관리자 화면에서 호출합니다. 대출금 입금은 팀원2의 입금 Service를 재사용합니다.
- 3, 6, 7, 8, 9, 11, 12, 15장(시연 시나리오 8번 포함)을 같은 방식으로 맞췄습니다.

## 4. 회원가입 · 계좌 개설: 본인확인 방식

**문제**: 기존에는 "회원가입 → 관리자 승인"이었는데, 관리자 기능은 5주차에 개발되기 때문에 2~4주차 개발이 막히는 구조였습니다. 또한 실제 은행은 회원가입을 직원이 승인하지 않습니다.

**실제 은행 방식 (참고)**
- 웹사이트/인터넷뱅킹 가입과 계좌 개설은 별개 절차이며, 가입은 본인 인증 후 즉시 완료됩니다.
- 엄격한 확인은 **첫 계좌 개설 시 실명확인**에서 이뤄집니다. 비대면 개설은 신분증 사본 제출, 타행 계좌 1원 인증, 영상통화 등 2가지 이상으로 확인합니다.
- 대포통장 방지를 위해 입출금 계좌는 보통 20영업일에 1개만 신규 개설할 수 있습니다.

**수정**: README에 **5-2장 "회원가입 · 계좌 개설 프로세스"**를 새로 추가했습니다.

```
회원가입 (휴대폰 인증 mock) → 즉시 정상 상태, 바로 로그인 가능
   ↓
첫 입출금 계좌 개설 신청
   - 신분증 정보 mock + 1원 인증 mock 입력
   - 계좌는 "개설대기(PENDING)"로 생성 (거래 불가)
   ↓
[관리자] 본인확인 심사
   ├─ 승인 → 회원 "확인완료", 계좌 "정상"
   └─ 반려 → 사유 입력, 계좌 "개설거절", 회원은 재신청 가능
   ↓
이후 계좌 개설, 예적금 가입, 카드 신청, 대출 신청은 즉시 가능
```

**정책**
- 본인확인 전에는 예적금 가입, 카드 신청, 대출 신청을 할 수 없습니다.
- 첫 계좌는 반드시 입출금 계좌이며, 예금·적금 계좌는 상품 가입으로만 생성합니다.
- 실제 주민번호 전체나 신분증 이미지는 저장하지 않습니다.
- `[선택]` 입출금 계좌 20영업일 1개 개설 제한 (영업일은 주말만 제외)

**DB 변경**
- `MEMBER`: 상태(정상/정지/탈퇴) + **실명확인상태(미확인/확인대기/확인완료/반려)** 추가
- `IDENTITY_VERIFICATION` 테이블 신설: 본인확인 신청·심사 이력 (반려 후 재신청 시 새 행 추가)
- `ACCOUNT` 상태에 **개설대기(PENDING), 개설거절(REJECTED)** 추가

**업무 분담 / 일정**
- 팀원1이 본인확인 로직을 맡고, 팀원2는 첫 계좌 개설 시 이를 호출합니다. 팀원4는 관리자 회원 관리 화면에서 승인/반려를 호출합니다.
- **2주차부터 "본인확인 완료" 테스트 회원을 시드 데이터로 준비**해 관리자 기능 없이 개발합니다. 실제 승인 흐름은 5주차에 연결해 테스트합니다.
- 시연 시나리오 1~2번을 "가입 → 계좌 개설대기 → 관리자 승인 → 계좌 정상" 흐름으로 바꿨습니다.

## 5. 거래 원장과 잔액의 관계 정리

**문제**: 11장은 "거래내역을 먼저 기록한 뒤 잔액 갱신", 15장은 "거래내역으로 잔액을 계산", extend 문서는 "잔액 갱신 후 거래내역 기록"으로 표현이 서로 달랐습니다.

**수정 (README 11장 설계 원칙)**
- `TRANSACTION_HISTORY`는 **거래 원장**입니다. 기록은 수정·삭제하지 않고, 취소는 반대 거래를 새로 기록합니다.
- `ACCOUNT.BALANCE`는 **현재 잔액을 저장해 두는 컬럼**입니다.
- 잔액 갱신과 원장 기록은 **하나의 트랜잭션**에서 함께 처리합니다. 둘 중 하나라도 실패하면 전체 롤백되므로 실행 순서는 정합성과 상관없습니다.
- **"계좌별 원장 합계 = ACCOUNT.BALANCE"** 검증 쿼리를 테스트 코드와 관리자 화면에 둡니다.

## 6. 이체 데드락 방지

**문제**: A→B 이체와 B→A 이체가 동시에 일어나면 서로 상대 계좌의 락을 기다리며 멈추는 **데드락**이 생길 수 있는데, 문서에 대책이 없었습니다.

**수정**: README에 **11-1장 "입출금/이체 트랜잭션 처리 규칙"**을 새로 추가했습니다.

1. 계좌 비밀번호 검증 (오류 횟수는 별도 트랜잭션으로 저장)
2. 비관적 락으로 계좌 조회 — **항상 계좌 ID가 작은 계좌부터** 잠금
3. 계좌 상태, 잔액, 1일 이체한도 검증
4. 잔액 갱신
5. 거래내역 2건 + 이체 1건 기록
6. 커밋 후 알림 이벤트 발행

```java
Long firstId  = Math.min(fromId, toId);
Long secondId = Math.max(fromId, toId);
Account first  = accountRepository.findByIdForUpdate(firstId);
Account second = accountRepository.findByIdForUpdate(secondId);
```

- 같은 계좌로 이체하면 락 전에 예외 처리하고, 락 대기 시간 제한을 둡니다.
- 3주차에 **동시 이체 테스트**(A→B, B→A 동시 실행)를 작성해 데드락이 없고 잔액 합계가 보존되는지 검증합니다.
- 발표 포인트에 "락 순서 고정으로 데드락 예방"을 추가했습니다.

## 9. 계좌 비밀번호 도입

**문제**: extend 문서에는 계좌 비밀번호가 있었지만 README에는 없었습니다. 구현 비용이 낮고 은행다운 기능이라 핵심 기능으로 넣었습니다.

**수정**
| 기능 | 우선순위 |
|---|---|
| 계좌 개설 시 4자리 비밀번호 설정 (BCrypt 해시 저장) | 핵심 |
| 출금·이체 시 비밀번호 검증 | 핵심 |
| 연속 5회 오류 시 계좌 잠금(LOCKED), 성공 시 오류 횟수 초기화 | 핵심 |
| 관리자 잠금 해제 | 핵심 |
| 계좌 비밀번호 변경 | 심화 |

- **동결(FROZEN)**은 관리자가 거는 거래 정지, **잠금(LOCKED)**은 비밀번호 오류로 자동 전환되는 상태로 구분합니다. 둘 다 출금/이체는 막고 입금은 허용합니다.
- 4자리 비밀번호는 경우의 수가 10,000개라 해시만으로는 부족하고, **5회 잠금이 실질적인 방어 수단**입니다. 그래서 오류 횟수는 이체가 롤백되어도 남도록 별도 트랜잭션(`REQUIRES_NEW`)으로 저장합니다.
- `ACCOUNT` 테이블에 계좌비밀번호, 비밀번호 오류횟수 컬럼을 추가했습니다.
- 시연 시나리오 13번(5회 오류 → 잠금 → 관리자 해제)을 추가했습니다.

## 고객·직원 분리와 직원 권한 3단계

## 지점/ATM 이용 가능 업무 테이블 분리 (BRANCH_SERVICE)

**문제**: `BRANCH.SERVICES` 컬럼에 "입금,출금,이체" 같은 자유 문자열을 저장하고 있었습니다. 값이 통일되지 않고, "입금 가능한 ATM" 같은 업무별 필터를 만들기 어려웠으며, 범위에서 제외한 `외환상담`이 시드에 섞여 있었습니다. 실제 쓰이는 곳도 화면 표시뿐이었습니다.

**결정 (B안)**: 업무를 별도 테이블 `BRANCH_SERVICE(BRANCH_ID, SERVICE_CODE)`로 분리하고, 업무 코드 7개를 고정했습니다.

| 코드 | 표시명 | ATM 가능 |
|---|---|:---:|
| `DEPOSIT` / `WITHDRAW` / `TRANSFER` / `BALANCE_INQUIRY` | 입금 / 출금 / 이체 / 잔액조회 | O |
| `ACCOUNT_OPENING` / `LOAN_CONSULTING` / `CARD_ISSUANCE` | 계좌개설 / 대출상담 / 카드발급 | X (창구 업무) |

### 변경 내용
- **DDL**: `BRANCH.SERVICES` 컬럼 삭제, `BRANCH_SERVICE` 테이블 추가 (PK로 중복 방지, CHECK로 코드 7개만 허용, 업무별 검색 인덱스)
- **시드**: 업무를 코드로 다시 입력, `외환상담` 제거

## 이체한도 변경: 감액은 즉시 반영, 증액만 심사

**문제**: 이체한도를 올리든 내리든 모두 MANAGER 승인이 필요했습니다. 실제 은행은 한도를 내리는 것은 더 안전해지므로 바로 반영합니다. 또 심사 중에 계좌 한도가 바뀌면 신청 당시 한도와 실제 한도가 어긋나는 문제가 있었습니다.

**결정**
| 구분 | 처리 |
|---|---|
| 감액 (희망 < 현재) | 신청 즉시 `APPROVED`, ACCOUNT 한도 바로 변경, 심사 직원 없음 |
| 증액 (희망 > 현재) | `PENDING` → MANAGER 승인/반려 |
| 심사 중 새 신청 | 같은 계좌에 심사 중인 신청이 있으면 감액 포함 새 신청 불가 |
| 승인 시 재확인 | 계좌의 현재 한도가 신청 당시와 다르면 승인 불가 → 반려 후 재신청 |

### 변경 내용
- **DDL**: `CK_TLR_DECREASE_AUTO` 추가 (감액은 항상 승인 상태, 심사 직원·일시 없음), `CK_TLR_REVIEWED` 수정 (처리된 증액 건만 심사 직원·일시 필수)
- **Java**: `TransferLimitRequest.request()`가 감액이면 바로 `APPROVED`. `isIncrease()`, `isAutoApproved()` 추가. `approve(reviewer, accountLimitNow)`로 승인 시 현재 한도 확인
- **문서**: table.md, faq.md(결정 사항 반영), README 8·10·11장, wireframes 30·33번 화면
- 도메인 규칙 검사 45개 통과 (이체한도 규칙 6개 추가)
