## 1. 프로젝트 개요

| 항목 | 내용 |
|---|---|
| 프로젝트명 | 모의 인터넷뱅킹 서비스 - 관리자 콘솔 |
| 한 줄 소개 | 은행 직원이 회원·계좌·거래·상품을 조회하고 운영 조치(이용 제한, 동결, 상품 등록)를 하는 관리자 전용 시스템 |
| 구분 | 4인 팀 프로젝트 중 관리자 파트 (1명) |

### 1.1 배경
- 실제 은행에서 회원가입, 계좌 개설, 대출 심사, 이체한도 변경의 승인 여부는 정해진 규칙에 따라 시스템이 판정하는 은행 업무다.
- 그래서 관리자 파트는 판정이 아니라 **운영·모니터링**을 맡는 것으로 범위를 다시 정한다.

### 1.2 목적
- 고객 서비스와 분리된 관리자 시스템(별도 경로, 별도 권한, 별도 화면)을 설계·구현해 본다.
- 금융 서비스의 감사 추적(누가, 언제, 무엇을, 왜 바꿨는지) 구조를 구현해 본다.

### 1.3 목표
1. 관리자 로그인과 권한 분리를 고객 로그인과 분리해 구현
2. 회원·계좌·거래·상품·대출 조회 화면 완성
3. 계좌 동결/해제, 회원 이용 제한 등 상태 변경 시 이력과 관리자 로그 100% 기록
4. 팀 시연 시나리오의 "계좌 동결 → 이체 차단" 시연

### 1.4 기대 효과
- 백오피스 시스템 구조(조회, 운영 조치, 감사 로그)를 설명할 수 있다.
- "관리자는 판정하지 않고 운영한다"는 실제 금융 시스템 원칙을 근거로 설계 의도를 설명할 수 있다.

## 2. 컨셉/방향

| 안 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **운영·모니터링 중심 (선택)** | 판정은 각 도메인의 시스템 규칙, 관리자는 조회·이용 제한·동결·상품 운영·감사 | 실제 구조와 맞음. 다른 파트를 막지 않음 | 팀 기획(컨셉 B 설명, 시연 1번) 수정 필요 |

**선택한 안:** 운영·모니터링 중심

**선택 이유**
1. 승인 판정은 은행 업무이고 각 도메인 담당자가 규칙으로 구현하는 게 맞다.
2. 관리자 승인이 없으면 다른 팀원이 관리자 개발을 기다리지 않아도 된다.
3. 감사 로그, 계좌 상태 이력처럼 금융 서비스다운 요소에 집중할 수 있다.

> ⚠️ 이 방향은 팀 README의 컨셉 B 정의를 바꾸므로 팀 합의가 먼저 필요하다 (11장).

## 3. 대상 사용자

| 사용자 | 권한 | 주요 이용 기능 |
|---|---|---|
| 총괄 관리자 | ROLE_SUPER_ADMIN (안) | 관리자 계정 발급·권한 부여, 전체 메뉴 |
| 운영 관리자 | ROLE_OPERATOR (안) | 회원·계좌·거래 조회, 이용 제한, 동결/해제 |
| 상품·고객지원 관리자 | ROLE_SERVICE (안) | 상품 관리, 공지·FAQ·문의 관리 |

> 역할 구분은 검토 중이다. 근거는 금융권의 직무 분리 원칙(한 사람이 요청과 승인을 모두 하지 않음). 처음에는 단일 ADMIN 권한으로 만들고 심화 단계에서 역할을 나눈다.

## 7. 기술 스택, 시스템 구성

| 구분 | 기술 | 비고 |
|---|---|---|
| 언어 | Java | 팀 공통 |
| 프레임워크 | Spring Boot, Spring MVC, Spring Security | 관리자용 SecurityFilterChain 별도 구성 |
| 데이터 접근 | MyBatis 또는 JPA | 팀 합의 |
| DB | Oracle | 팀 공통 |
| 화면 | HTML/CSS/JS (Thymeleaf), 차트 라이브러리 | 고객 사이트와 별도 디자인 |
| 통신 | REST API | `/api/admin/**` |
| 실시간 통신 | WebSocket (STOMP) | 탐지 알림, 실시간 거래 현황을 관리자 화면에 즉시 전송 |
| 캐시/집계 | Redis | 계좌별 최근 이체 횟수·금액을 쌓아 FDS 규칙을 즉시 판정 |
| 이벤트 처리 | Spring 이벤트, 트랜잭션 커밋 후 리스너, 비동기 처리 | 이체 완료 → 탐지 → 알림을 이체 처리와 분리 |
| 외부 알림 (선택) | 이메일 발송 (Spring Mail) | 담당자가 접속해 있지 않을 때 보조 알림 |
| 형상관리 | Git, GitHub | `feature/admin-*` 브랜치 |

### 시스템 구성도

```text
[고객 사이트]  /           ── 고객 SecurityFilterChain ──┐
                                                         ├─ Service ─ Oracle
[관리자 콘솔]  /admin      ── 관리자 SecurityFilterChain ─┘     │
                                                                └─ ADMIN_LOG, ACCOUNT_STATUS_HISTORY

[이체 완료] → FDS 규칙 판정 (Redis 집계) → 탐지 기록 → 담당자 알림 (WebSocket + 알림함) → 담당자 확인 → 고객 연락 → 해제 또는 동결
```

- 관리자는 고객 도메인의 데이터를 **직접 UPDATE하지 않고**, 각 도메인 서비스(예: 계좌 상태 변경 메서드)를 호출한다.

## 12. 결과물, 발표 계획

### 12.1 최종 산출물
- 관리자 파트 기획서, 요구사항 정의서, 기능명세서
- 관리자 화면 와이어프레임, 관리자 API 명세
- 관리자 콘솔 소스코드

### 12.2 시연 시나리오 (관리자 부분)
1. 관리자 로그인 (고객 로그인과 다른 경로)
2. 대시보드에서 회원 수·거래량 확인
3. 회원 검색 → 상세 → 로그인 이력 확인
4. 계좌 검색 → 동결 (사유 입력)
5. (고객 계정) 동결 계좌로 이체 시도 → 차단
6. 계좌 상태 이력, 관리자 활동 로그에서 동결 기록 확인
7. 상품 등록 → 고객 상품 목록에 반영 확인
8. (고객 계정) 짧은 시간에 고액 이체 반복 → 이상거래 대응 담당자 화면에 실시간 알림 → 탐지 건 확인 → 고객 연락 결과 입력 → 계좌 동결 또는 정상 처리

### 12.3 발표 강조 포인트
- 판정(시스템)과 운영(관리자)을 분리한 이유
- 모든 상태 변경에 남는 이력과 감사 로그
- 고객 시스템과 분리된 관리자 인증 구조
