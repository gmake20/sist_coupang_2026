# GoodPang 프로젝트 상세 구성

`발표.md`가 발표용 스크립트(개요 → 아키텍처 → 시연 흐름)라면, 이 문서는 **레퍼런스용**입니다.
실제 디렉터리 구조, 패키지별 파일 수, URL 매핑 방식, DB 구조를 코드베이스를 직접 뒤져서 정리했습니다.
(2026-09-05 기준, `feature/scm` 브랜치)

## 3. 두 개의 컨트롤러 패턴이 공존하는 이유

이 프로젝트는 원래 **서블릿 하나 = URL 하나**(`@WebServlet` 애노테이션) 방식으로 시작했고, 지금도 대부분(89/92)의
기능이 이 방식입니다. 그런데 2026-09-04에 팀원(flicker1016)이 `/product`, `/category`, `/option` 3개 URL만
**커맨드 패턴**으로 리팩터링했습니다.

```
                          [기존 방식 - 89개 서블릿]
브라우저 → @WebServlet(예: "/vendor/order") → Servlet.doGet/doPost → DAO → JSP forward


                          [신규 커맨드 패턴 - 3개 URL]
브라우저 → web.xml <servlet-mapping>(/product, /category, /option)
        → DispatcherServlet.process()
        → commandHandler.properties 에서 URL → Handler 클래스 조회 (init() 시점에 리플렉션으로 1회 생성)
        → CommandHandler.process() 실행 (예: CategoryHandler)
        → 내부에서 XxxService 호출 (예: CategoryService)
        → Service 가 기존 DAO(CategoryProductDAO 등)를 그대로 호출
        → Handler 가 view 경로(JSP) 문자열을 리턴 → DispatcherServlet 이 forward (또는 "redirect:" 접두사면 리다이렉트)
```

- **왜 이렇게 갈렸나**: 같은 URL에 서블릿을 두 개 등록할 수 없어서, 기존 `ProductServlet`/`CategoryServlet`/
  `ProductOptionServlet`의 `@WebServlet` 애노테이션만 주석 처리하고 클래스는 "비교용"으로 그대로 남겨뒀습니다.
  실제로 도는 코드는 `DispatcherServlet` → `command.XxxHandler` → `service.XxxService`입니다.
- **DAO는 그대로 재사용**: `CategoryService`/`ProductOptionService`는 새 SQL을 만들지 않고 기존
  `CategoryProductDAO`/`ProductOptionDAO`/`ProductImageDAO`를 그대로 호출합니다. 즉 이 리팩터링은
  DB 접근 계층이 아니라 **Controller 계층(서블릿 → Dispatcher+Handler)만 바꾼 것**입니다.
- **`load-on-startup`을 일부러 안 씀**: `commandHandler.properties`에 오타가 있어도 앱 전체가 죽지 않고
  그 URL만 에러가 나도록, 처음 그 URL이 호출될 때 지연 초기화되게 해둠(web.xml 주석 참고).
- 나머지 89개 서블릿은 이 리팩터링과 무관하게 원래 방식 그대로 동작합니다 — 팀원 코드에 영향 없음.

## 5. 인증 필터 3종

| 필터 | 적용 범위 | 방식 |
|---|---|---|
| `AdminAuthFilter` | `/admin/*` (와일드카드) | `/admin/login`만 검사 제외(무한루프 방지). 세션에 `loginAdmin` 없으면 원래 URL을 `adminRedirectAfterLogin`에 저장 후 로그인 페이지로 |
| `VendorAuthFilter` | `/vendor/dashboard`, `/vendor/product` 등 URL을 **하나하나 나열** | 세션에 `loginSeller` 없으면 `vendorRedirectAfterLogin`에 저장 후 `/vendor/login`으로 |
| `CacheControlFilter` | `/*` (전체) | 모든 응답에 `Cache-Control: no-cache, no-store, must-revalidate` 등 헤더 추가 — 로그아웃 후 뒤로가기로 캐시된 화면이 보이는 것 방지 |

세 필터 모두 `web.xml` 등록 없이 `@WebFilter` 애노테이션만으로 자동 등록됩니다.
서블릿 안에서도 세션 체크를 한 번 더 하는 경우가 많은데(이중 방어), 필터가 못 막는 `DispatcherServlet`
경유 URL(`/product`, `/category`, `/option`)은애초에 로그인 없이도 볼 수 있는 페이지라 해당 없음.

## 6. 이미지 URL 처리 (`img:url` / `ImageUrl`)

DB에는 상품/판매자 이미지 경로가 `upload/5/xxx.jpg`처럼 **도메인/컨텍스트패스 없이** 저장되어 있습니다.
화면에 실제로 보여주려면 환경에 맞는 접두사를 붙여야 하는데, 이걸 한 곳에서 처리합니다.

- `com.goodpang.util.ImageUrl.resolve(String)` — `os.name`으로 로컬 Windows 개발 환경인지 판단해서
  - Windows(개발자 PC)면 절대 URL(`http://scym3.cafe24.com:8080/...`)을 붙임
  - 그 외(Ubuntu 운영 서버)면 `contextPath`를 붙임
- JSP에서는 `WEB-INF/goodpang-functions.tld`로 등록한 커스텀 EL 함수 `${img:url(경로)}`로 호출
- `contextPath` 값 자체는 `ImageBaseUrlListener`(`ServletContextListener`)가 앱 시작 시 한 번만 `ImageUrl.init()`에 주입
- AJAX로 이미지 경로를 다시 받아오는 곳(`/option` 응답의 `imageUrls`, 상품 등록 화면의 `optionsJson`)도
  전부 서버 쪽에서 `ImageUrl.resolve()`를 거쳐 완성된 URL을 내려주고, JS는 받은 값을 그대로 씀
  (예전엔 JS가 `contextPath + '/' + url`로 직접 조립해서 로컬 개발 환경에서 옵션 변경 시 이미지가 깨지는
  버그가 있었음 — 2026-09-04/05에 수정됨)

## 7. 로그, 승인 상태 등 운영 관련 구조

- **액션 로그**: `VENDOR_ACTION_LOG`(판매자가 한 일), `ADMIN_ACTION_LOG`(관리자가 한 일) 두 테이블.
  대상이 `PRODUCT`/`ORDERS`/`SELLER`/`DELIVERY` 등 여러 테이블이라 FK 대신
  `TARGET_TYPE` + `TARGET_NO` 조합의 **폴리모픽 연관**으로 가리킴.
- **판매자 승인 상태(`SELLER.APPROVAL_STATUS`)**: `입점 대기` → (사업자정보 제출) → `심사 중` → 관리자 승인 →
  `승인` / 반려 시 `반려`. 그 외 `정지`, `탈퇴`가 있음.
  - `승인`이 아닌 판매자는 `/vendor/product/write`에서 폼 자체가 안 뜨고 안내 화면만 보임(2026-09-05 추가).
  - `/vendor/business-info`로 정보를 다시 제출하면, `입점 대기`/`반려` 상태였을 때만 `심사 중`으로 바뀌고
    이미 `승인`된 판매자가 정보만 고치는 경우는 상태가 유지됨(2026-09-04 수정 — 원래는 무조건 재심사로 돌아갔음).
- **타임존**: `web.xml`의 `jakarta.servlet.jsp.jstl.fmt.timeZone=Asia/Seoul` context-param으로
  `fmt:formatDate`가 항상 한국시간을 쓰도록 고정(2026-09-04 추가 — 이전엔 서버 JVM 기본 타임존에 따라
  UTC로 보이는 문제가 있었음).

## 8. 데이터베이스 구조 개요

| 영역 | 주요 테이블 |
|---|---|
| 계정 | `MEMBER`, `SELLER`, `ADMIN` |
| 상품 | `CATEGORY`(재귀 자기참조), `PRODUCT`, `PRODUCT_OPTION`, `PRODUCT_IMAGE`, `PRODUCT_TAG`, `PRODUCT_NOTICE` |
| 주문/결제 | `ORDERS`, `ORDER_DETAIL`, `ORDER_ADDRESS`, `CART`, `PAYMENT`, `PAYMENT_METHOD` |
| 배송 | `DELIVERY` |
| 부가서비스 | `REVIEW`, `NOTICE`, `WOW_MEMBERSHIP`, `WOW_PAYMENT` |
| 운영/로그 | `VENDOR_ACTION_LOG`, `ADMIN_ACTION_LOG`, `PRODUCT_VIEW_LOG` |

- `CATEGORY`: `category_no`/`parent_category_no`/`category_level`(1~5) 자기참조 구조. 대분류 15개 아래
  중분류 → 소분류(→ 필요 시 더 아래 단계까지) 트리. Oracle `START WITH ... CONNECT BY PRIOR`로
  "이 카테고리 + 하위 전부"를 한 번에 조회(`CategoryProductDAO.CATEGORY_TREE_CONDITION`).
  대분류 1~7은 실측(캡처) 기반, 8~15는 실측 자료가 없어 같은 규칙으로 새로 설계해 채움
  (`docs/category_table_insert.sql` 참고).
- `PRODUCT_OPTION.PRICE`/`NORMAL_PRICE`는 절대가가 아니라 `PRODUCT.PRODUCT_PRICE`(기본가)에 더해지는
  **가감액**. 최종 판매가 = `PRODUCT_PRICE + NVL(옵션가, 0)`.
- DB 스키마는 팀원별로 문서가 나뉘어 있고(`docs/table.md`, `docs/상품.md`, `docs/판매자.md`,
  `docs/쿠팡_ERD.md`), 일부 테이블(`CATEGORY`, `PRODUCT`, `PRODUCT_OPTION`, `PRODUCT_IMAGE`,
  `PRODUCT_TAG`, `PRODUCT_NOTICE`, `VENDOR_ACTION_LOG`, `ADMIN_ACTION_LOG`, `NOTICE`,
  `PRODUCT_VIEW_LOG`)는 `docs/*_table_create.sql`로 재실행 가능한 DDL이 따로 있음.

## 9. CI/CD (Slack 기반 배포)

`cicd/README.md`, `cicd.md`에 자세히 있고 여기선 요약만.

```
로컬에서 git push
   ↓
Slack "/restart" (권한 있는 유저만, slack_restart_bot.py 가 검사)
   ↓
서버의 restart.sh 실행
   ├─ git pull (sist_coupang_2026)
   ├─ src/main/java 전체를 javac 컴파일 (WEB-INF/lib/* + Tomcat lib/* classpath)
   ├─ webapp 내용 + 컴파일된 class 를 합쳐 GoodPang.war 로 패키징
   ├─ Tomcat 종료(최대 30초 대기) → 기존 ROOT 삭제 → 새 war를 ROOT.war로 복사
   └─ Tomcat 재시작
   ↓
성공/실패 로그가 Slack 채널에 다시 응답으로 올라옴
```

- `set -e`가 걸려있어 **컴파일 에러 시 Tomcat을 내리기 전에 스크립트가 중단** — 빌드 실패해도 기존
  서비스는 안 죽음.
- Slack Bolt(Socket Mode)라서 공인 IP/포트포워딩/HTTPS 엔드포인트 없이 아웃바운드 웹소켓만으로 동작.

## 10. 의존 라이브러리 (`WEB-INF/lib`)

| jar | 용도 |
|---|---|
| `gson-2.14.0.jar` | JSON 직렬화 (AJAX 응답, optionsJson 등) |
| `jakarta.servlet.jsp.jstl-3.0.1.jar` / `jakarta.servlet.jsp.jstl-api-3.0.2.jar` | JSTL(`c:`, `fmt:` 태그, 커스텀 EL 함수) |
| `jbcrypt-0.4.jar` | 비밀번호 해시(BCrypt) — 회원/판매자/관리자 공통 |
| `lombok.jar` | DTO의 `@Getter`/`@Setter` 등 보일러플레이트 제거 |
| `ojdbc8.jar` | Oracle JDBC 드라이버 |

Maven 중앙 저장소 없이 서버에서 직접 빌드하는 구조라, 새 라이브러리가 필요하면 jar를
`WEB-INF/lib`에 직접 커밋해야 함(9장 CI/CD 참고).
