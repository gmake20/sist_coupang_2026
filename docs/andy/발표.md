# GoodPang 프로젝트 구조 설명 (발표용)

쿠팡을 벤치마킹한 이커머스 웹서비스 **GoodPang**의 전반적인 구조 설명 스크립트.
"이 프로젝트가 뭘 하는지" → "어떻게 나눠져 있는지" → "데이터가 어떻게 흐르는지" → "어떻게 배포되는지" 순서로 구성했습니다.

---

## 1. 프로젝트 개요

- **GoodPang** — 쿠팡(Coupang)을 참고해서 만든 오픈마켓형 이커머스 서비스
- 하나의 서비스 안에 **세 종류의 사용자**가 각자 다른 화면/권한으로 들어옴
  - **구매자(Member)** — 상품을 검색·구매하는 일반 회원
  - **판매자(Seller)** — 입점해서 상품을 등록·판매하는 사업자 (쿠팡의 "쿠팡윙"에 해당)
  - **관리자(Admin)** — 판매자 입점심사, 상품 승인, 배송 관리 등 운영을 담당
- 기술 스택: **Java / JSP / Servlet(Jakarta EE) / Oracle Database**, Tomcat 10.1 위에서 동작
- 패턴: **MVC** (Servlet=Controller, DAO+DTO=Model, JSP=View)를 프로젝트 전체에 일관되게 적용

---

## 2. 전체 아키텍처

```
요청(브라우저)
   │
   ▼
Filter (인증 검사) ── AdminAuthFilter / VendorAuthFilter / CacheControlFilter
   │
   ▼
Servlet (Controller) ── 파라미터 파싱, 흐름 제어, 세션 확인
   │
   ▼
DAO (Model) ── SQL 작성/실행, PreparedStatement, 트랜잭션 관리
   │
   ▼
Oracle DB
   │
   ▼
DTO (데이터 객체) ── DAO ↔ Servlet ↔ JSP 사이에서 데이터를 담아 나름
   │
   ▼
JSP (View) ── JSTL/EL로 화면 렌더링, 필요 시 서블릿에 폼 제출
```

- 서블릿 92개, DAO 38개, DTO 49개, 필터 3개로 구성 (2026-09-04 기준)
- 로그인 여부는 **세션**(`loginMember` / `loginSeller` / `loginAdmin`)으로 관리하고, 판매자·관리자 전용 URL은 각각 `VendorAuthFilter`/`AdminAuthFilter`가 필터 단계에서 한 번에 막아줌 — 서블릿마다 로그인 체크 코드를 반복하지 않아도 되는 구조
- 정적 리소스(CSS/JS/이미지)는 `Tomcat`이 웹앱 캐시로 서빙하고, `CacheControlFilter`가 캐시 정책을 조정

### 2-1. Servlet(Controller) 자세히

Servlet은 **비즈니스 로직(SQL) 자체는 DAO에 위임**하고, 아래 세 가지만 책임지는 얇은 계층입니다. 그래서 대부분의 서블릿이 20~60줄 정도로 짧게 유지됩니다.

**① 세션 확인** — 거의 모든 `doGet`/`doPost`의 첫 줄
```java
HttpSession session = request.getSession(false);
SellerDTO loginSeller = (session != null) ? (SellerDTO) session.getAttribute("loginSeller") : null;

if (loginSeller == null) {
    response.sendRedirect(request.getContextPath() + "/vendor/login");
    return;
}
```
필터가 먼저 막아주는 URL도 있지만 서블릿도 자체적으로 한 번 더 체크하고, 세션에서 꺼낸 `sellerNo`는 이후 DAO 호출마다 "이 사람이 자기 것만 건드리는지" 검증하는 기준이 됩니다.

**② 파라미터 파싱** — 문자열로 들어온 요청값을 숫자/날짜로 변환하고, 잘못된 값은 조용히 기본값 처리
```java
private LocalDate parseDate(String value) {
    if (value == null || value.isBlank()) return null;
    try {
        return LocalDate.parse(value);
    } catch (DateTimeParseException e) {
        return null;
    }
}
```
파일 업로드가 있는 서블릿(`VendorBusinessInfoServlet`, `VendorProductWriteServlet`)은 `request.getPart(...)`로 멀티파트를 읽어 디스크에 저장하고 경로만 DTO에 담습니다.

**③ 흐름 제어** — GET은 조회 후 JSP로 `forward`, POST는 처리 후 `redirect`(PRG 패턴, 새로고침해도 중복 제출 안 되게)
```java
// GET: 화면 진입
request.setAttribute("orderList", orderList);
request.getRequestDispatcher("/WEB-INF/views/vendor-order.jsp").forward(request, response);

// POST: 처리 후 리다이렉트
optionDAO.updateOption(...);
response.sendRedirect(request.getContextPath() + "/vendor/product/options");
```
DAO 결과에 따른 분기도 여기서 처리합니다 — 예를 들어 `VendorOrderShipServlet`은 `ShipResult`(SUCCESS/INVOICE_DUPLICATE/FAILED)를 받아 성공이면 목록으로, 중복 송장번호면 에러 파라미터를 붙여 같은 화면으로 되돌립니다.

## 3. 세 사용자 영역별 기능 구조

### 3-1. 구매자(Member) 사이트
- 회원가입/로그인/정보수정
- 상품 탐색: 카테고리(대/중/소분류 재귀 구조) → 상품 목록 → 상품 상세
- 장바구니 → 주문/결제 → 배송지·결제수단 관리
- 주문내역 조회, 주문취소/반품
- 상품 리뷰 작성/조회
- 와우(WOW) 유료 멤버십 가입/해지, 무료배송 혜택

### 3-2. 판매자센터(Vendor)
- 판매자 회원가입 → 사업자정보 입력(정산계좌·서류) → **입점심사**(대기/심사중/승인/반려)
- 판매자 대시보드 — 오늘 주문수/매출, 매출 현황(일/주/월 그래프), 방문자수/상품노출수
- 상품 등록(카테고리·옵션·이미지) → 관리자 승인 → 상품 목록/노출관리
- 상품 옵션관리 — 재고·가격·품절여부를 표에서 바로 수정
- 주문/배송/출고 관리 — 주문 목록(검색 필터) → 출고 대기(송장 등록) → 배송중(지연 감지) → 배송완료
- 정산관리 — 정산내역 리스트(주 단위 매출·수수료·정산금액) → 정산상세(주문별 내역 + 입금계좌)
- 판매자 정보관리, 회원탈퇴

### 3-3. 관리자(Admin)
- 관리자 로그인/대시보드
- 판매자 입점심사(승인/반려), 판매자 정지
- 상품 승인/반려
- 배송완료 처리 (배송기사 역할을 임시로 대행)
- 판매자 액션 로그 / 관리자 액션 로그 조회(검색 기능 포함)
- 공지사항 관리

## 4. 데이터베이스 구조 개요

핵심 테이블은 세 사용자 축을 그대로 반영합니다.

| 영역 | 주요 테이블 |
|---|---|
| 계정 | `MEMBER`, `SELLER`, `ADMIN` |
| 상품 | `CATEGORY`(재귀 자기참조), `PRODUCT`, `PRODUCT_OPTION`, `PRODUCT_IMAGE` |
| 주문/결제 | `ORDERS`, `ORDER_DETAIL`, `CART`, `PAYMENT`, `PAYMENT_METHOD` |
| 배송 | `DELIVERY`, `ORDER_ADDRESS`, `DELIVERY_ADDRESS` |
| 부가 서비스 | `REVIEW`, `PRODUCT_RETURN`, `WOW_MEMBERSHIP`, `WOW_PAYMENT`, `NOTICE` |
| 운영/로그 | `VENDOR_ACTION_LOG`, `ADMIN_ACTION_LOG`, `PRODUCT_VIEW_LOG` |

- `CATEGORY`는 대분류/중분류/소분류를 테이블 하나로 통합한 **자기참조 재귀 구조**(`parent_category_no`)
- `PRODUCT_OPTION.PRICE`는 절대 판매가가 아니라 `PRODUCT.product_price`에 더해지는 **가감액** — 최종가는 두 값을 더해서 계산
- `VENDOR_ACTION_LOG`/`ADMIN_ACTION_LOG`는 대상 테이블이 여러 개(`PRODUCT`/`ORDERS`/`SELLER`...)라 FK 대신 `target_type`+`target_no`로 가리키는 **폴리모픽 연관** 구조
- 초기 ERD(23개 테이블) 대비 실제 구현 과정에서 `PAYMENT_METHOD`/`PRODUCT_IMAGE`/`PRODUCT_VIEW_LOG` 등이 새로 생기고, `PRODUCT`/`SELLER`/`REVIEW` 등은 컬럼이 크게 확장·조정됨 (자세한 변경 이력은 [`update_table.md`](update_table.md), [`쿠팡_ERD.md`](쿠팡_ERD.md) 참고)

## 5. 인증/캐시 필터

Filter 3개는 각자 역할이 다릅니다.

### AdminAuthFilter
- 적용 범위: `/admin/*` (와일드카드 — `/admin` 이하 전부 자동 적용)
- `/admin/login`만 검사 대상에서 빼서, 로그인 페이지 자체가 "로그인 안 했으니 로그인 페이지로 리다이렉트"를 반복하는 **무한루프**를 막음
- 세션에 `loginAdmin`이 없으면 원래 가려던 URL(쿼리스트링 포함)을 `adminRedirectAfterLogin`에 저장해두고 로그인 페이지로 보냄 — 로그인 성공 후 원래 페이지로 돌아가기 위함

### VendorAuthFilter
- 적용 범위: `/admin`처럼 와일드카드가 아니라, **URL을 하나하나 나열**한 방식(`/vendor/dashboard`, `/vendor/product`, `/vendor/order` 등)
- 세션에 `loginSeller`가 없으면 `vendorRedirectAfterLogin`에 저장 후 `/vendor/login`으로 리다이렉트 — 회원(Member) 로그인의 리다이렉트 키와 겹치지 않도록 이름을 다르게 씀


### CacheControlFilter
- 적용 범위: `/*` (사이트 전체, 로그인 여부와 무관하게 모든 응답에 적용)
- 인증과는 무관 — 모든 응답에 `Cache-Control: no-cache, no-store, must-revalidate` / `Pragma: no-cache` / `Expires: 0` 헤더를 붙여서 브라우저가 페이지를 캐시하지 못하게 함
- 로그아웃 후 브라우저 "뒤로가기"를 눌러도 캐시된 이전 로그인 화면이 그대로 보이는 걸 방지하는 용도

세 필터 다 `web.xml` 등록 없이 `@WebFilter` 애노테이션만으로 자동 등록됩니다.

## 6. 배포/운영

- Ubuntu 서버 + Tomcat 10.1, WAR 배포
- **Slack Bolt 봇**으로 배포 자동화 — Slack에서 `/restart` 명령 한 번으로 `git pull → war 배포 → Tomcat 재시작`까지 원클릭 처리 (공인 IP/포트포워딩 불필요, Socket Mode로 동작)
- 정적 리소스 캐시, DB 커넥션 풀(JNDI) 등 운영 중 발견된 이슈들을 설정으로 튜닝하며 안정화 (자세한 트러블슈팅은 [`cicd.md`](cicd.md) 참고)

## 7. 발표 흐름 제안

1. **개요** — 어떤 서비스인지, 세 사용자 축(구매자/판매자/관리자) 한 장으로 소개
2. **아키텍처** — MVC 구조 다이어그램으로 "요청이 어떻게 처리되는지" 한 번 보여주기
3. **핵심 시나리오 시연** — 구매자가 주문 → 판매자가 배송 처리 → 관리자가 승인/모니터링, 하나의 흐름으로 이어서 시연 (팀원별 담당 화면 시연은 여기서 이어짐)
4. **DB 구조** — 사용자 축과 맞물리는 테이블 관계를 간단히
5. **배포/운영** — CI/CD 자동화까지 보여주면 "실제로 돌아가는 서비스"라는 인상을 줄 수 있음

개인 담당 파트 상세 시연 목록은 [`movie_play_list.md`](movie_play_list.md) 참고.
