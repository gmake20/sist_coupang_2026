# GoodPang 프로젝트 구조 설명 (발표용)

쿠팡을 벤치마킹한 이커머스 웹서비스 **GoodPang**의 전반적인 구조 설명 스크립트.
"이 프로젝트가 뭘 하는지" → "어떻게 나눠져 있는지" → "데이터가 어떻게 흐르는지" → "어떻게 배포되는지" 순서로 구성했습니다.

---

## 1. 프로젝트 개요

- **GoodPang** — 쿠팡(Coupang)을 참고해서 만든 오픈마켓형 이커머스 서비스
- 하나의 서비스 안에 **세 종류의 사용자**가 각자 다른 화면/권한으로 들어옴
  - **구매자(Member)** — 상품을 검색·구매하는 일반 회원
  - **판매자(Seller)** — 입점해서 상품을 등록·판매하는 사업자 (쿠팡의 "쿠팡윙"에 해당)
  - **관리자(Admin)** — 판매자 입점심사, 상품 승인, 배송 관리 등 운영을 담당
- 기술 스택: **Java / JSP / Servlet(Jakarta EE) / Oracle Database**, Tomcat 10.1 위에서 동작
- 패턴: **MVC** (Servlet=Controller, DAO+DTO=Model, JSP=View)를 프로젝트 전체에 일관되게 적용

---

## 2. 전체 아키텍처

```
요청(브라우저)
   │
   ▼
Filter (인증 검사) ── AdminAuthFilter / VendorAuthFilter / CacheControlFilter
   │
   ▼
Servlet (Controller) ── 파라미터 파싱, 흐름 제어, 세션 확인
   │
   ▼
DAO (Model) ── SQL 작성/실행, PreparedStatement, 트랜잭션 관리
   │
   ▼
Oracle DB
   │
   ▼
DTO (데이터 객체) ── DAO ↔ Servlet ↔ JSP 사이에서 데이터를 담아 나름
   │
   ▼
JSP (View) ── JSTL/EL로 화면 렌더링, 필요 시 서블릿에 폼 제출
```

- 서블릿 92개, DAO 38개, DTO 49개, 필터 3개로 구성 (2026-09-04 기준)
- 로그인 여부는 **세션**(`loginMember` / `loginSeller` / `loginAdmin`)으로 관리하고, 판매자·관리자 전용 URL은 각각 `VendorAuthFilter`/`AdminAuthFilter`가 필터 단계에서 한 번에 막아줌 — 서블릿마다 로그인 체크 코드를 반복하지 않아도 되는 구조
- 정적 리소스(CSS/JS/이미지)는 `Tomcat`이 웹앱 캐시로 서빙하고, `CacheControlFilter`가 캐시 정책을 조정

### 2-1. Servlet(Controller) 자세히

Servlet은 **비즈니스 로직(SQL) 자체는 DAO에 위임**하고, 아래 세 가지만 책임지는 얇은 계층입니다. 그래서 대부분의 서블릿이 20~60줄 정도로 짧게 유지됩니다.

**① 세션 확인** — 거의 모든 `doGet`/`doPost`의 첫 줄
```java
HttpSession session = request.getSession(false);
SellerDTO loginSeller = (session != null) ? (SellerDTO) session.getAttribute("loginSeller") : null;

if (loginSeller == null) {
    response.sendRedirect(request.getContextPath() + "/vendor/login");
    return;
}
```
필터가 먼저 막아주는 URL도 있지만 서블릿도 자체적으로 한 번 더 체크하고, 세션에서 꺼낸 `sellerNo`는 이후 DAO 호출마다 "이 사람이 자기 것만 건드리는지" 검증하는 기준이 됩니다.

**② 파라미터 파싱** — 문자열로 들어온 요청값을 숫자/날짜로 변환하고, 잘못된 값은 조용히 기본값 처리
```java
private LocalDate parseDate(String value) {
    if (value == null || value.isBlank()) return null;
    try {
        return LocalDate.parse(value);
    } catch (DateTimeParseException e) {
        return null;
    }
}
```
파일 업로드가 있는 서블릿(`VendorBusinessInfoServlet`, `VendorProductWriteServlet`)은 `request.getPart(...)`로 멀티파트를 읽어 디스크에 저장하고 경로만 DTO에 담습니다.

**③ 흐름 제어** — GET은 조회 후 JSP로 `forward`, POST는 처리 후 `redirect`(PRG 패턴, 새로고침해도 중복 제출 안 되게)
```java
// GET: 화면 진입
request.setAttribute("orderList", orderList);
request.getRequestDispatcher("/WEB-INF/views/vendor-order.jsp").forward(request, response);

// POST: 처리 후 리다이렉트
optionDAO.updateOption(...);
response.sendRedirect(request.getContextPath() + "/vendor/product/options");
```
DAO 결과에 따른 분기도 여기서 처리합니다 — 예를 들어 `VendorOrderShipServlet`은 `ShipResult`(SUCCESS/INVOICE_DUPLICATE/FAILED)를 받아 성공이면 목록으로, 중복 송장번호면 에러 파라미터를 붙여 같은 화면으로 되돌립니다.

## 3. 세 사용자 영역별 기능 구조

### 3-1. 구매자(Member) 사이트
- 회원가입/로그인/정보수정
- 상품 탐색: 카테고리(대/중/소분류 재귀 구조) → 상품 목록 → 상품 상세
- 장바구니 → 주문/결제 → 배송지·결제수단 관리
- 주문내역 조회, 주문취소/반품
- 상품 리뷰 작성/조회
- 와우(WOW) 유료 멤버십 가입/해지, 무료배송 혜택

### 3-2. 판매자센터(Vendor)
- 판매자 회원가입 → 사업자정보 입력(정산계좌·서류) → **입점심사**(대기/심사중/승인/반려)
- 판매자 대시보드 — 오늘 주문수/매출, 매출 현황(일/주/월 그래프), 방문자수/상품노출수
- 상품 등록(카테고리·옵션·이미지) → 관리자 승인 → 상품 목록/노출관리
- 상품 옵션관리 — 재고·가격·품절여부를 표에서 바로 수정
- 주문/배송/출고 관리 — 주문 목록(검색 필터) → 출고 대기(송장 등록) → 배송중(지연 감지) → 배송완료
- 정산관리 — 정산내역 리스트(주 단위 매출·수수료·정산금액) → 정산상세(주문별 내역 + 입금계좌)
- 판매자 정보관리, 회원탈퇴

### 3-3. 관리자(Admin)
- 관리자 로그인/대시보드
- 판매자 입점심사(승인/반려), 판매자 정지
- 상품 승인/반려
- 배송완료 처리 (배송기사 역할을 임시로 대행)
- 판매자 액션 로그 / 관리자 액션 로그 조회(검색 기능 포함)
- 공지사항 관리

## 4. 데이터베이스 구조 개요

핵심 테이블은 세 사용자 축을 그대로 반영합니다.

| 영역 | 주요 테이블 |
|---|---|
| 계정 | `MEMBER`, `SELLER`, `ADMIN` |
| 상품 | `CATEGORY`(재귀 자기참조), `PRODUCT`, `PRODUCT_OPTION`, `PRODUCT_IMAGE` |
| 주문/결제 | `ORDERS`, `ORDER_DETAIL`, `CART`, `PAYMENT`, `PAYMENT_METHOD` |
| 배송 | `DELIVERY`, `ORDER_ADDRESS`, `DELIVERY_ADDRESS` |
| 부가 서비스 | `REVIEW`, `PRODUCT_RETURN`, `WOW_MEMBERSHIP`, `WOW_PAYMENT`, `NOTICE` |
| 운영/로그 | `VENDOR_ACTION_LOG`, `ADMIN_ACTION_LOG`, `PRODUCT_VIEW_LOG` |

- `CATEGORY`는 대분류/중분류/소분류를 테이블 하나로 통합한 **자기참조 재귀 구조**(`parent_category_no`)
- `PRODUCT_OPTION.PRICE`는 절대 판매가가 아니라 `PRODUCT.product_price`에 더해지는 **가감액** — 최종가는 두 값을 더해서 계산
- `VENDOR_ACTION_LOG`/`ADMIN_ACTION_LOG`는 대상 테이블이 여러 개(`PRODUCT`/`ORDERS`/`SELLER`...)라 FK 대신 `target_type`+`target_no`로 가리키는 **폴리모픽 연관** 구조
- 초기 ERD(23개 테이블) 대비 실제 구현 과정에서 `PAYMENT_METHOD`/`PRODUCT_IMAGE`/`PRODUCT_VIEW_LOG` 등이 새로 생기고, `PRODUCT`/`SELLER`/`REVIEW` 등은 컬럼이 크게 확장·조정됨 (자세한 변경 이력은 [`update_table.md`](update_table.md), [`쿠팡_ERD.md`](쿠팡_ERD.md) 참고)

## 5. 인증/캐시 필터

Filter 3개는 각자 역할이 다릅니다.

### AdminAuthFilter
- 적용 범위: `/admin/*` (와일드카드 — `/admin` 이하 전부 자동 적용)
- `/admin/login`만 검사 대상에서 빼서, 로그인 페이지 자체가 "로그인 안 했으니 로그인 페이지로 리다이렉트"를 반복하는 **무한루프**를 막음
- 세션에 `loginAdmin`이 없으면 원래 가려던 URL(쿼리스트링 포함)을 `adminRedirectAfterLogin`에 저장해두고 로그인 페이지로 보냄 — 로그인 성공 후 원래 페이지로 돌아가기 위함

### VendorAuthFilter
- 적용 범위: `/admin`처럼 와일드카드가 아니라, **URL을 하나하나 나열**한 방식(`/vendor/dashboard`, `/vendor/product`, `/vendor/order` 등)
- 세션에 `loginSeller`가 없으면 `vendorRedirectAfterLogin`에 저장 후 `/vendor/login`으로 리다이렉트 — 회원(Member) 로그인의 리다이렉트 키와 겹치지 않도록 이름을 다르게 씀


### CacheControlFilter
- 적용 범위: `/*` (사이트 전체, 로그인 여부와 무관하게 모든 응답에 적용)
- 인증과는 무관 — 모든 응답에 `Cache-Control: no-cache, no-store, must-revalidate` / `Pragma: no-cache` / `Expires: 0` 헤더를 붙여서 브라우저가 페이지를 캐시하지 못하게 함
- 로그아웃 후 브라우저 "뒤로가기"를 눌러도 캐시된 이전 로그인 화면이 그대로 보이는 걸 방지하는 용도

세 필터 다 `web.xml` 등록 없이 `@WebFilter` 애노테이션만으로 자동 등록됩니다.

## 7. 발표 흐름 제안

1. **개요** — 어떤 서비스인지, 세 사용자 축(구매자/판매자/관리자) 한 장으로 소개
2. **아키텍처** — MVC 구조 다이어그램으로 "요청이 어떻게 처리되는지" 한 번 보여주기
3. **핵심 시나리오 시연** — 구매자가 주문 → 판매자가 배송 처리 → 관리자가 승인/모니터링, 하나의 흐름으로 이어서 시연 (팀원별 담당 화면 시연은 여기서 이어짐)
4. **DB 구조** — 사용자 축과 맞물리는 테이블 관계를 간단히
5. **배포/운영** — CI/CD 자동화까지 보여주면 "실제로 돌아가는 서비스"라는 인상을 줄 수 있음

개인 담당 파트 상세 시연 목록은 [`movie_play_list.md`](movie_play_list.md) 참고.

### 8-1. (p19, 슬라이드 10) 구현 화면 ④ — 담당 소개

> "저는 판매자 파트 개발을 담당한 신창만입니다. 제가 구현한 기능은 크게 5가지입니다."

- **판매자 회원가입·입점심사** — 판매자 회원가입/로그인, 입점 대기·승인·반려 처리, 관리자의 판매자 관리(정지 기능 포함)
- **상품 등록·옵션 관리** — 옵션·이미지 업로드를 포함한 상품 등록, 상품 옵션관리, 카테고리 UI, 상품 승인 연동
- **판매자 대시보드·매출현황** — 일/주/월별 매출 그래프, 방문자수 집계, 판매자 액션 로그(검색 기능 포함)
- **주문·배송·정산 관리** — 주문/배송관리, 출고·운송장 관리, 취소·반품·교환 관리, 정산내역, 배송완료 로그
- **Github 생성 및 CI/CD 배포 자동화** — Slack Bolt 봇(`/restart`)으로 서버 `git pull → war 배포 → Tomcat 재시작`을 원클릭 자동화, 배포 흐름도 문서화

사용 기술 태그: `JSP` · `Transaction` · `MVC`

#### 8-1-1. 판매자 회원가입·입점심사 상세 — 2026-09-07 보강

`SELLER.APPROVAL_STATUS` 하나의 컬럼이 판매자 계정의 전체 생애주기를 표현합니다.

```
회원가입(VendorSignupServlet)
   │  INSERT ... APPROVAL_STATUS = '입점 대기'
   ▼
입점 대기 ──(사업자정보 제출)──► 심사 중 ──(관리자 승인)──► 승인 ──(관리자 정지)──► 정지 ──(정지 해제)──┐
   ▲                                │                                                              │
   └────────────(관리자 반려)────── 반려 ◄────────────────────────────────────────────────────────┘
                                                                                          (재승인 시 다시 '승인')
```
(그 외 `탈퇴` 상태도 있으며, `정지`와 마찬가지로 로그인 자체가 막힘)

**① 회원가입 — `VendorSignupServlet` (`POST /vendor/signup`)**
- 필수값 검사 → 비밀번호 확인 일치 + 8자 이상 검사 → `bizType` 값 변환(`individual`→개인사업자, `corporate`→법인사업자)
- **이메일 중복**(`SellerDAO.existsByEmail`)과 **사업자등록번호 중복**(`existsByBusinessNo`)을 각각 별도로 검사 — 사업자등록번호 하나로 여러 계정을 만드는 것도 막음
- 비밀번호는 평문 저장 없이 `BCrypt.hashpw()`로 해시해서 저장
- `SellerDAO.insertSeller()`로 INSERT — 이 시점엔 상호명·대표자명·담당자명·연락처·사업자정보만 있고, 아직 **사업장 주소/정산계좌/서류**는 없는 상태. `APPROVAL_STATUS`는 무조건 `'입점 대기'`로 시작

**② 로그인 — `VendorLoginServlet` (`POST /vendor/login`)**
- 이메일로 조회 후 `BCrypt.checkpw()`로 비밀번호 검증
- **`정지`/`탈퇴` 상태일 때만 로그인 자체를 차단**한다는 게 포인트 — `정지`면 반려사유 컬럼(`REJECT_REASON`)에 저장된 정지 사유까지 에러 메시지에 같이 보여줌
- 그 외 상태(`입점 대기`/`심사 중`/`반려`/`승인`)는 **전부 로그인을 허용**하고, 상태별 안내는 로그인 이후 대시보드 배너에서 분기 처리 — "로그인은 되는데 뭘 해야 하는지 화면에서 안내"하는 방식
- 로그인 성공 시 세션에 `loginSeller`/`sellerNo`/`storeName` 저장, 세션 타임아웃 30분. 로그인 전에 원래 가려던 URL이 있었으면(`vendorRedirectAfterLogin`) 거기로, 없으면 `/vendor/dashboard`로 리다이렉트

**③ 사업자 추가정보 제출 — `VendorBusinessInfoServlet` (`POST /vendor/business-info`)**
- 로그인한 판매자만 접근 가능. 사업장 주소, 통신판매업신고번호, 대표 판매 카테고리, 정산계좌(은행명/계좌번호/예금주), **사업자등록증·통신판매신고증 파일 첨부**를 입력받음
- **최초 제출 시엔 서류 2종 첨부가 필수**지만, 이미 첨부된 판매자가 다른 정보만 고치러 온 경우엔 파일을 새로 안 올려도 기존 파일 URL을 그대로 유지(`saveUploadedFile`이 새 파일 없으면 `existingUrl` 반환)
- 상태 전환 로직이 SQL의 `CASE WHEN`으로 되어 있는 게 핵심:
  ```sql
  APPROVAL_STATUS = CASE WHEN APPROVAL_STATUS IN ('입점 대기', '반려') THEN '심사 중' ELSE APPROVAL_STATUS END
  ```
  → `입점 대기`나 `반려` 상태에서 제출하면 심사 대상이니 `심사 중`으로 바뀌지만, **이미 `승인`된 판매자가 정산계좌만 살짝 고치는 경우까지 재심사로 되돌리지 않는다**는 게 트러블슈팅 포인트였음(2026-09-04 수정 — 원래는 무조건 재심사로 돌아가던 버그였음)
  - 발표에서 이 부분을 강조하면 좋음: "왜 그냥 UPDATE로 안 하고 CASE WHEN을 썼는지" 질문 나오기 좋은 포인트
- 처리 성공 후 세션의 `loginSeller`를 DB에서 다시 조회해 최신 상태로 갱신(`session.setAttribute`) — 안 하면 방금 바뀐 심사상태가 화면에 바로 반영이 안 됨

**④ 관리자의 입점심사·정지 처리 — `SellerListServlet`/`SellerDetailServlet`/`SellerApprovalServlet`**
- `GET /admin/sellers` — 전체 판매자 목록(`SellerDAO.findAll`), `GET /admin/seller-detail?sellerNo=` — 판매자 한 명 상세
- `POST /admin/seller-approve`가 `action` 파라미터 하나로 4가지를 다 처리:
  | action | 결과 상태 | 비고 |
  |---|---|---|
  | `approve` | `승인` | 기존 반려/정지 사유를 `null`로 지움 |
  | `reject` | `반려` | 사유 미입력 시 기본 문구로 대체 |
  | `suspend` | `정지` | **`REJECT_REASON` 컬럼을 정지 사유 저장용으로도 재사용**(별도 컬럼을 안 만들고 기존 컬럼을 겸용) |
  | `reactivate` | `승인` | 정지 해제 = 다시 승인 상태로 |
- 4가지 액션 전부 `AdminActionLogDAO.log()`로 **관리자 액션 로그**(`ADMIN_ACTION_LOG`)에 남김 — "누가, 언제, 어떤 판매자를, 무슨 사유로" 처리했는지 감사 추적 가능

> "판매자 하나의 상태를 컬럼 하나(`APPROVAL_STATUS`)로 관리하면서, 회원가입 직후엔 '입점 대기'로 시작해서
> 사업자정보를 제출하면 '심사 중', 관리자가 승인하면 '승인'으로 바뀝니다. 반려되면 사유와 함께 다시
> 정보를 제출할 수 있고, 승인된 이후에도 문제가 생기면 관리자가 '정지'시킬 수 있는데, 이때는
> 로그인 자체가 막힙니다. 그리고 이 승인/반려/정지 처리는 전부 관리자 액션 로그에 남도록 만들어서
> 나중에 누가 어떤 조치를 했는지 추적할 수 있게 했습니다."

#### 8-1-2. 상품 등록·옵션 관리 상세 — 2026-09-07 보강

슬라이드에 있는 4가지 소항목(옵션·이미지 업로드 포함 상품등록 / 상품옵션관리 / 카테고리 UI / 상품승인 연동) 순서로 정리했습니다.

**① 카테고리 UI — 검색어 자동완성 (`GET /category/getinfo?keyword=`, `CategoryInfo` 서블릿)**
- 상품등록 화면 캡처(8-2)에 보이는 "의류" 검색창이 이 API를 호출함
- 그냥 이름이 비슷한 카테고리를 다 보여주는 게 아니라, **자식이 없는 리프 카테고리(=실제로 상품을 등록할 수 있는 소분류)만** 검색 대상으로 함(`NOT EXISTS (자식 카테고리)` 조건)
- 같은 이름의 리프가 다른 상위 카테고리 밑에도 있을 수 있어서(예: "의류"가 남성패션에도, 여성패션에도 있음), Oracle `CONNECT BY`로 리프 → 루트까지 거슬러 올라가며 `SYS_CONNECT_BY_PATH`로 전체 경로("패션의류/잡화 > 남성패션 > 의류")를 같이 만들어서 내려줌 — 그래서 자동완성 목록에 같은 이름이 여러 개 떠도 사용자가 구분할 수 있음
- 이 API는 검색어 없이 호출하면(`keyword` 파라미터 없음) 대분류~소분류 3단계 트리 전체를 재귀 조회해서 반환하는 별도 경로도 있음(다른 화면의 카테고리 셀렉트박스용)

**② 상품 등록 — `VendorProductWriteServlet` (`POST /vendor/product/write`)**
- **입점 승인된 판매자만 접근 가능**: `doGet`에서 `loginSeller.getApprovalStatus()`가 `'승인'`이 아니면 등록 폼 대신 `vendor-product-write-locked.jsp`(안내 화면)를 보여줌. `doPost`도 동일 조건을 한 번 더 검사(403)
- 검증 순서: 로그인 → 승인상태 → 사업자 주소 등록 여부 → (멀티파트 파싱 자체가 실패했는지) → 노출상품명/등록상품명/기본가격/출고지 필수값 → 옵션 1개 이상
  - `request.getParts()`를 검증 로직 맨 앞에서 먼저 호출하는 게 포인트: `getParameter()`는 멀티파트 파싱이 실패해도 그냥 `null`을 반환해서 원인을 알 수 없는데, `getParts()`는 실패 시 `IllegalStateException`을 던져서 "이미지 용량 초과" 같은 원인을 구분해 사용자에게 안내할 수 있게 함
- 등록 시 `PRODUCT.SALE_STATUS`는 무조건 `'승인 대기'`로 시작 (④에서 이어짐)
- 옵션은 최소 1개 필수 — "옵션 없음(단일 상품)"도 옵션 1개짜리 레코드로 등록됨
- 이미지는 옵션별 대표 1장 + 추가 이미지, 상품 상세설명 이미지까지 전부 `UploadPaths` 기준 디스크에 저장 후 URL만 DTO에 담아 `PRODUCT_IMAGE`에 저장(8장 6-1절 참고)
- `PRODUCT`/`PRODUCT_OPTION`/`PRODUCT_IMAGE` 세 테이블 Insert가 끝나면 `VendorActionLogDAO`로 "상품 등록" 액션 로그를 남김

**옵션 가격 모델 (발표 포인트)**: `PRODUCT_OPTION.PRICE`/`NORMAL_PRICE`는 절대 판매가가 아니라 `PRODUCT.PRODUCT_PRICE`(기본가)에 더해지는 **가감액**입니다. 예를 들어 기본가 19,000원인 상품에 "L 사이즈는 +2,000원" 옵션이 있으면 최종 판매가는 21,000원이 되는 식 — 쿠팡 실제 서비스의 옵션가 방식을 참고해서 설계했습니다.

**③ 상품 옵션 관리 — `VendorProductOptionListServlet`/`VendorProductOptionUpdateServlet`**
- `GET /vendor/product/options` — 판매자의 **상품을 가로질러 옵션 단위로** 조회(상품별 필터 드롭다운 지원), 화면에서는 같은 상품의 옵션들을 rowspan으로 묶어서 표시(`groupByProduct`)
- `POST /vendor/product/option/update` — 표에서 판매가·정상가·재고수량·품절여부를 바로 수정. 발표 포인트: **`PRODUCT_OPTION`에는 `SELLER_NO`가 없어서**, `PRODUCT`를 조인한 `EXISTS` 서브쿼리로 "이 옵션이 로그인한 판매자 소유가 맞는지" 확인한 뒤에만 UPDATE되게 만듦 — 다른 판매자의 옵션번호를 URL/폼 조작으로 넣어도 안 바뀌는 구조
- 수정 성공 시 `VendorActionLogDAO`에 "옵션 수정" 로그(판매가/재고/상태 요약 포함)를 남김
- 판매 중지/재개는 옵션이 아니라 **상품 단위**로 별도 처리 — `VendorProductSaleStatusServlet`(`POST /vendor/product/status`)가 `'판매 중' ↔ '판매 중지'`만 전환(승인 대기·품절 상태는 안 건드림)

**④ 상품 승인 연동 — `AdminProductApprovalServlet`**
- 판매자가 등록하면 `'승인 대기'` 상태라 노출/구매가 안 되고(트러블슈팅 8-5-①에서 다룬 그 버그가 이 상태 체크 로직), 관리자가 `POST /admin/product-approve`로 승인해야 `'판매 중'`으로 바뀌어 실제 노출됨
- **설계상의 트레이드오프 하나**: `PRODUCT.SALE_STATUS`는 CHECK 제약으로 `'판매 중'/'품절'/'판매 중지'/'승인 대기'` 네 가지만 허용되고 별도의 `'반려'` 상태나 반려사유 컬럼이 없습니다. 그래서 관리자가 상품을 반려하면 실제로는 **`'판매 중지'`로 전환하는 것으로 대신**하고 있습니다 — 판매자 쪽(회원가입·입점심사)은 반려 상태와 사유 컬럼이 따로 있는 것과 대비되는 부분이라, 질문 나오면 "상품 쪽은 아직 반려 사유를 남기는 구조까지는 못 갔다"고 솔직하게 답하면 됩니다.

> "상품 등록은 승인된 판매자만 들어갈 수 있고, 카테고리는 검색어로 리프 카테고리만 찾아서 전체 경로까지
> 보여주도록 만들었습니다. 등록된 상품은 '승인 대기' 상태로 시작해서 관리자가 승인해야 실제로 노출되고요,
> 옵션 가격은 기본가에 옵션별 가감액을 더하는 방식으로 설계했습니다. 옵션 관리 화면에서는 재고나 가격을
> 표에서 바로 수정할 수 있는데, 이때 다른 판매자 옵션을 못 건드리게 소유권 검증을 서브쿼리로 걸어뒀습니다."

#### 8-1-3. 판매자 대시보드·매출현황 상세 — 2026-09-07 보강

`VendorDashboardServlet`(`GET /vendor/dashboard`)이 `VendorDashboardDAO`의 5개 메서드를 호출해서 화면 하나를 채웁니다.

**① 오늘(선택일) KPI 카드 4개 — `getTodayStat()` → `VendorDashboardStatDTO`**
- 오늘 주문수·매출, 오늘 방문자수·상품노출수를 **어제와 같은 날짜에 같이 집계**해서 증감률까지 한 번에 계산
- 주문수·매출은 `ORDER_DETAIL`을 이 판매자 상품 기준으로 조인하고 `ORDER_STATUS != '주문취소'`로 취소 건을 제외
- 방문자수/상품노출수는 `PRODUCT_VIEW_LOG`(상품 상세페이지 조회 로그) 기준 — **방문자수는 `SESSION_ID` 기준 중복 제거**(같은 사람이 여러 번 봐도 1명), **노출수는 조회 건수 그대로**(같은 사람이 3번 보면 3회) — 이 둘의 차이를 명확히 구분해서 집계
- 증감률 계산의 예외 처리도 신경 씀: 어제 값이 0이면 나눗셈이 안 되니, 오늘도 0이면 0%, 오늘 값이 생겼으면 100%로 취급(`changePercent()`)

**② 날짜 선택 — `?date=yyyy-MM-dd`**
- 대시보드 상단 날짜 선택 UI에서 고른 날짜를 서블릿이 파싱해서(`parseSelectedDate`) DAO 전체에 파라미터로 넘김 — 이게 바로 **8-5 트러블슈팅 ③번(대시보드 날짜선택 미반영 버그)**에서 고친 부분입니다. 예전엔 쿼리마다 `SYSDATE`가 하드코딩돼 있어서 어떤 날짜를 골라도 항상 오늘 기준으로만 나왔는데, 지금은 `targetDate`를 파라미터로 받아서 KPI·그래프·스파크라인이 전부 선택한 날짜 기준으로 다시 계산됨
- 미래 날짜를 넣거나 형식이 잘못되면 오늘 날짜로 자동 대체(`parseSelectedDate`), 드롭다운에는 최근 3일(오늘/어제/그제)만 옵션으로 노출

**③ 매출 현황 그래프(일/주/월) — `getDailySalesStat`/`getWeeklySalesStat`/`getMonthlySalesStat`**
- 세 메서드 다 같은 패턴: **"날짜 스핀"(연속된 7일/5주/5개월 목록을 `CONNECT BY LEVEL`로 미리 만들고) 실적 서브쿼리를 `LEFT JOIN`**하는 구조 — 그래서 주문이 하나도 없는 날/주/월도 0으로 채워져서 그래프에 항상 7칸·5칸이 빠짐없이 나옴(실적 서브쿼리만 쓰면 주문 없는 날짜가 통째로 빠져버림)
- 주간은 `TRUNC(date, 'IW')`(월요일 시작 ISO 주), 월간은 `TRUNC(date, 'MM')`으로 그룹핑
- 서버가 `Gson`으로 JSON 문자열을 만들어 `request.setAttribute`로 넘기고, JSP `<script>`에서 `const dailyStat = ${dailySalesJson};` 식으로 그대로 JS 객체에 꽂아 씀(8-2에서 볼 `optionsJson` AJAX 패턴과 달리, 여기는 페이지 로드 시점에 이미 값이 박혀서 내려감)
- **그래프 축 최댓값을 하드코딩하지 않고 실데이터 기준으로 동적 계산**(`niceMax()`) — 판매자마다 매출 규모가 다른데 축 상한이 고정이면 매출이 작은 판매자는 막대가 거의 안 보이고 큰 판매자는 넘쳐버리는 문제가 있어서, 실제 최댓값의 1.2배를 보기 좋은 단위로 올림 처리

**④ KPI 카드 스파크라인 — `renderSparkline()`**
- 각 KPI 카드 안의 미니 꺾은선 그래프는 별도로 값을 다시 조회하지 않고, **일간 매출 데이터(`dailyStat`)와 방문 추이 데이터(`dailyTraffic`)를 그대로 재사용**해서 그림(주문수/매출은 `dailyStat`에서, 방문자수/노출수는 별도 `getDailyTrafficStat()` 결과에서 뽑음)

**⑤ 판매자 액션 로그(검색 기능)** — 정확히는 **판매자 본인이 아니라 관리자가** `AdminVendorActionLogListServlet`에서 특정 판매자의 활동 이력을 검색·조회하는 기능입니다. 로그 자체는 이 판매자가 상품 등록·옵션 수정·상품 숨김·판매중지 등 실제 액션을 할 때마다 `VendorActionLogDAO.log()`가 `VENDOR_ACTION_LOG` 테이블에 쌓아둔 것 — 대시보드에 직접 보이는 위젯은 아니지만, "판매자가 뭘 했는지 다 로그로 남긴다"는 이 대시보드 파트의 운영 철학과 이어지는 부분이라 슬라이드에 같이 소개된 것으로 보입니다.

> "대시보드는 오늘 주문수·매출·방문자수·상품노출수를 어제와 비교해서 보여주고, 날짜를 다른 날로
> 선택하면 그 날짜 기준으로 전부 다시 계산됩니다. 매출 그래프는 일간·주간·월간을 다 실데이터로
> 보여주는데, 주문이 없는 날짜도 빠지지 않도록 날짜 스핀을 만들어서 실적을 왼쪽 조인하는 방식으로
> 처리했고, 그래프 축 눈금도 판매자 매출 규모에 맞게 동적으로 계산되도록 만들었습니다."

#### 8-1-4. 주문·배송·정산 관리 상세 — 2026-09-07 보강

이 파트는 화면이 여러 개(주문 목록 / 출고·운송장 / 배송 모니터링 / 취소·반품·교환 / 정산)로 나뉘어 있지만, 전부 `ORDER_DETAIL`을 판매자 상품 기준으로 조회하는 같은 패턴을 씁니다.

**① 주문/배송관리 — `VendorOrderServlet` (`GET /vendor/order`)**
- 판매자의 상품이 포함된 주문을 **주문 라인(`ORDER_DETAIL`) 단위**로 보여줌(한 주문에 이 판매자 상품이 여러 줄 있으면 여러 행으로 표시)
- 검색 필터 3종(주문일 범위, 주문상태, 배송상태, 결제상태)에 페이지네이션까지 지원 — 발표 포인트: **이 셋이 사실 전부 `ORDER_STATUS` 컬럼 하나를 서로 다른 관점으로 보는 것**이라는 설계
  - `orderStatus`: 결제완료/배송중/배송완료/주문취소 (실제 값 그대로)
  - `deliveryStatus`: 출고대기(=결제완료)/배송중/배송완료 (배송 진행도 관점)
  - `paymentStatus`: 결제완료(=주문취소 아님)/결제취소(=주문취소) — "결제대기"는 시스템에 없는 상태라 옵션 자체를 안 둠(8-1-3에서 다룬 내용과 이어짐)
  - 세 필터를 동시에 서로 안 맞게 걸면 0건이 나올 수 있는데, 이건 버그가 아니라 애초에 서로 다른 값을 요구한 것이므로 정상 동작이라고 코드에 명시적으로 남겨둠
- 우측 "배송 현황" 도넛과 상단 통계 카드는 `VendorOrderStatSummaryDTO`(`countStats()`)로 별도 집계 — 여기도 마찬가지로 실제 있는 상태(출고대기/배송중/배송완료)만 집계하고, 대응 상태가 없는 "신규주문/결제대기/상품준비중/취소반품교환"은 "준비 중"으로 표시(지난 대화에서 다룬 내용)

**② 출고·운송장 관리 — `VendorShippingServlet`(`GET /vendor/shipping`) + `VendorOrderShipServlet`(`POST /vendor/order/ship`)**
- `VendorShippingServlet`은 **출고 대기(`결제완료`) 상태인 주문만** 모아서 보여주고, 결제완료 후 **2일이 지나도 출고 안 된 건은 "출고 지연"**으로 표시(`VendorShippingDTO.isDelayed()`)
- 실제 송장 등록·출고 처리(`결제완료 → 배송중` 전환)는 화면을 새로 안 만들고 **주문 목록 화면과 동일한 `/vendor/order/ship`을 재사용** — `redirectTo` 파라미터로 "어느 화면에서 눌렀는지"를 받아서 처리 후 그 화면으로 돌려보냄
  - 보안 포인트: `redirectTo` 값을 그대로 리다이렉트에 쓰지 않고, **화이트리스트(`/vendor/shipping`만 허용, 그 외는 기본값 `/vendor/order`)로 검증**해서 오픈 리다이렉트를 막음
- `shipOrder()` 트랜잭션 안에서 **같은 택배사 + 같은 송장번호 조합이 이미 있는지 확인**해서 중복이면 `ShipResult.INVOICE_DUPLICATE`로 구분해 반환(택배사가 다르면 번호가 겹쳐도 허용) — 화면에는 `?shipError=duplicateInvoice`로 원인이 넘어가서 "송장번호 중복"이라고 구체적으로 안내 가능
- `ORDERS`에는 `SELLER_NO`가 없어서, `ORDER_DETAIL`/`PRODUCT`로 이 주문에 이 판매자의 상품이 실제 포함돼 있는지 확인한 후에만 처리(소유권 검증)

**③ 배송 관리 — `VendorDeliveryServlet` (`GET /vendor/delivery`)**
- **배송중인 주문을 모니터링**하는 화면 — 배송 시작일로부터 **3일이 지나도 완료 안 되면 "배송 지연"**으로 표시(`VendorDeliveryDTO.isDelayed()`, 출고 지연의 2일보다 임계치가 더 김)
- 이 화면에서 배송완료 처리를 직접 하지는 않음 — 실제로는 배송기사가 앱에서 처리해야 할 일인데, 배송기사용 화면이 아직 없어서 **관리자가 `/admin/deliveries`에서 대행 중**(④에서 이어짐)

**④ 취소·반품·교환 관리 — `VendorReturnServlet`/`VendorReturnDAO` (`GET /vendor/return`)**
- `PRODUCT_RETURN` 테이블에 취소/반품/교환을 구분하는 컬럼이 따로 없고 `RETURN_STATUS`라는 문자열 컬럼만 있어서, **`RETURN_STATUS LIKE '취소%'/'반품%'/'교환%'`로 유형을 나눠서** 화면에 탭처럼 카운트(`cancelCount`/`returnCount`/`exchangeCount`)를 보여줌
- **현재는 주문취소(`OrderCancelDAO.cancelOrder`)만 실제로 이 테이블에 `'취소완료'` 상태로 데이터가 쌓이고, 반품/교환은 구매자 쪽 신청 화면이 아직 없어서 데이터가 비어있을 수 있음** — 발표에서 정직하게 짚고 넘어가면 좋은 부분("현재는 취소 흐름만 실제로 동작하고, 반품·교환은 데이터 구조만 준비된 상태")

**⑤ 정산관리 — `VendorSettlementServlet`/`VendorSettlementDetailServlet` (`GET /vendor/settlement`, `/vendor/settlement/detail`)**
- **배송완료(`ORDER_STATUS='배송완료'`) 처리된 주문**을, 배송완료일(`DELIVERY.DELIVERY_END_DATE`) 기준 **월요일 시작 1주 단위**(`TRUNC(.., 'IW')`)로 묶어서 매출을 집계 → 리스트 화면(주차별 요약) → 상세 화면(그 주에 포함된 주문라인 전체)으로 드릴다운
- **발표에서 꼭 짚어야 할 한계점**: 수수료율(10%)과 정산주기(기간 종료 후 7일 뒤 지급)가 **실제 값이 아니라 코드에 상수로 박아둔 가정치**입니다 — DB 어디에도(SELLER/PRODUCT/CATEGORY) 수수료 관련 컬럼이 없어서, 카테고리별/판매자 등급별로 다른 수수료를 매기려면 별도 테이블 설계가 더 필요하다는 걸 `VendorSettlementDTO` 주석에 명시해뒀습니다. "제한된 시간 안에서 정산의 전체 흐름(집계→수수료 차감→지급일 계산→상세 조회)은 구현했지만, 실제 수수료 정책까지는 반영하지 못했다"고 솔직하게 설명하면 됩니다.

**⑥ 배송완료 로그 — `AdminDeliveryCompleteServlet`**
- 배송완료는 관리자가 대행 처리하지만(③ 참고), 처리 순간 **관리자 액션 로그(`ADMIN_ACTION_LOG`)와 판매자 액션 로그(`VENDOR_ACTION_LOG`) 양쪽에 동시에 기록**됩니다
- 흥미로운 부분: 완료 처리 대상 주문에 **여러 판매자의 상품이 섞여 있을 수 있어서**, `CompleteResult.getSellerNos()`로 관련된 판매자 전원에게 각자 "배송 완료" 로그를 하나씩 남김 — 한 주문 = 한 판매자라고 가정하지 않고 멀티 판매자 주문을 전제로 설계된 부분

> "주문/배송/정산은 화면은 여러 개지만 전부 판매자 상품이 포함된 주문 라인을 기준으로 조회한다는
> 공통점이 있습니다. 출고 지연은 2일, 배송 지연은 3일 기준으로 자동으로 잡아주고, 송장번호는
> 같은 택배사 내에서 중복이면 등록이 안 되게 막았습니다. 정산은 배송완료된 주문을 주 단위로 묶어서
> 수수료를 뗀 금액과 지급 예정일을 보여주는데, 지금은 수수료율 10%를 고정값으로 가정해서 계산하고
> 있고, 실제 서비스라면 카테고리별로 다른 수수료 테이블이 별도로 필요한 부분입니다."

#### 8-1-5. Github 생성 및 CI/CD 배포 자동화 상세 — 2026-09-07 보강

8-4(p22 CI/CD 플로우차트 슬라이드)가 "발표 화면에 보이는 5단계"를 다뤘다면, 여기는 그 뒤에 있는 **실제 스크립트/봇 코드** 기준으로 더 파고든 내용입니다. (`cicd/README.md`, `cicd/deploy/restart.sh`, `cicd/slack-restart-bot/slack_restart_bot.py` 기준 — 참고로 저장소에 예전 버전 문서인 `docs/andy/cicd.md`가 남아있는데, 그건 지금 방식으로 바뀌기 **전**(war를 미리 빌드해서 `cdcdtest`라는 별도 저장소에 커밋해두던 방식) 기록이라 최신 상태와 다릅니다 — 발표 준비하시면서 옛 문서 보고 헷갈리지 않게 미리 적어둡니다.)

**① Github 생성 — 공유 소스 저장소**
- 팀이 함께 쓰는 저장소는 `https://github.com/gmake20/sist_coupang_2026.git` 하나 — 로컬에서 여기로 `git push`하면, 서버의 `restart.sh`가 같은 저장소를 `/root/git/sist_coupang_2026`에 clone/pull해서 그대로 빌드 재료로 씀
- 즉 "로컬 저장소"와 "서버가 빌드에 쓰는 저장소"가 완전히 같은 히스토리를 보고 있어서, 로컬에서 커밋한 내용과 서버에 배포되는 내용이 항상 1:1로 대응됨(중간에 별도 빌드 저장소를 안 거침)

**② 설계 변화 (발표에서 강조하면 좋은 포인트) — "왜 서버에서 직접 빌드하도록 바꿨는가"**
- 예전 방식: 개발자가 **로컬 Eclipse에서 war를 export** → war 전용 저장소(`cdcdtest`)에 commit/push → 서버는 그 저장소를 pull만 받아서 배포. 즉 "빌드는 사람이, 배포만 자동화"였음
- 지금 방식: `project/GoodPang`이 Maven 표준 레이아웃(`src/main/java`/`src/main/webapp`)이고 의존 라이브러리(gson/lombok/jbcrypt/ojdbc8/jstl 등)가 전부 `WEB-INF/lib`에 커밋돼 있다는 걸 활용해서, **서버가 소스에서 직접 `javac`+`jar`로 war를 빌드**하도록 바꿈 → Eclipse export 단계와 `cdcdtest` 저장소를 통째로 없앰
- 이 변화의 의미: "빌드까지 완전 자동화"가 된 것 — 사람이 개입하는 지점이 `git push`와 Slack `/restart` 입력, 딱 두 곳만 남음

**③ `restart.sh` 상세 동작** (`cicd/deploy/restart.sh`, 서버의 `/root/restart.sh`)
```bash
if [ -d "$SRC_REPO_DIR/.git" ]; then git pull; else git clone "$SRC_REPO_URL"; fi   # 최초 1회는 clone, 이후는 pull
javac -d build/classes -cp "WEB-INF/lib/*:/opt/tomcat/lib/*" @sources.txt          # Tomcat lib까지 클래스패스에 포함
cp -r webapp/. staging/ && cp -r build/classes/. staging/WEB-INF/classes/
jar cf GoodPang.war -C staging .
/opt/tomcat/bin/shutdown.sh
# pgrep으로 프로세스 완전 종료를 최대 30초 대기 (안 기다리면 war 교체 중 파일 잠김 문제 발생 가능)
rm -rf webapps/ROOT && cp GoodPang.war webapps/ROOT.war
sh /opt/tomcat/bin/startup.sh
```
- 저장소가 서버에 아직 없으면(최초 실행) `git clone`, 있으면 `git pull`로 분기 — 서버를 새로 세팅해도 스크립트 하나로 처리되게 함
- `javac` 클래스패스에 `WEB-INF/lib/*`뿐 아니라 **Tomcat 자체의 `lib/*`도 포함**해야 함 — 서블릿 API(`jakarta.servlet.*`) 같은 건 프로젝트가 아니라 Tomcat이 들고 있는 라이브러리라서 이걸 빼먹으면 컴파일이 안 됨
- `set -e`가 파일 맨 위에 있어서, **`javac` 컴파일 에러가 나는 순간 스크립트가 즉시 멈추고 그 아래 `shutdown.sh`(Tomcat 종료)까지 안 감** — 그래서 배포 실패가 곧바로 "서비스 중단"으로 이어지지 않고, 기존에 떠 있던 서비스가 계속 유지됨

**④ Slack 봇 상세 동작** (`cicd/slack-restart-bot/slack_restart_bot.py`)
- 권한 검사가 **2단계**: `ALLOWED_SLACK_USER_IDS`(허용된 사용자인지) + `ALLOWED_SLACK_CHANNEL_ID`(허용된 채널에서 호출했는지) — 둘 다 통과해야 실행, 실패하면 "이 명령을 실행할 권한이 없습니다" 응답만 하고 끝(로그에는 누가 시도했는지 기록)
- `subprocess.run(["bash", RESTART_SCRIPT_PATH], capture_output=True, timeout=RESTART_TIMEOUT_SEC)`으로 `restart.sh`를 실행 — **stdout/stderr를 캡처**하고, 종료코드로 성공(`0`)/실패를 구분해서 각각 다른 이모지(✅/❌)와 함께 Slack에 결과를 그대로 붙여줌
- 타임아웃(기본 180초)과 그 외 예외를 **따로 구분**해서 처리 — 타임아웃이면 "서버에서 직접 확인해달라"고 안내(스크립트가 죽지 않고 계속 돌고 있을 수도 있으니 무작정 재시도하면 안 됨)
- Slack 메시지 길이 제한을 넘지 않도록 `truncate()`로 출력을 3500자에서 잘라서 전송

**⑤ 서버 인프라 쪽 트러블슈팅 (CI/CD와 맞닿아 있는 실전 이슈)**
- **Tomcat 계정 문제**: `slack-restart-bot.service`가 처음엔 `User=ubuntu`로 돼 있었는데, 실제 서버 로그인 계정은 `root`뿐이라(`ubuntu` 계정 자체가 없음) 서비스가 "unavailable resources" 에러로 기동 실패 → `User=root`로 재작성 + `.env` 파일 누락 문제까지 같이 해결
- **업로드 용량 제한(`maxPostSize`)**: 상품등록 화면에서 옵션 이미지를 여러 장 첨부하면 `Failed to fetch`가 떴던 버그가 있었는데, 원인이 애플리케이션 코드(`@MultipartConfig`)가 아니라 **Tomcat 커넥터 자체의 기본 업로드 제한(2MB)**이었음. `server.xml`은 war에 포함 안 되는 **컨테이너 설정**이라 배포 자동화(`/restart`)로는 절대 손대지지 않는 부분이라, 이건 서버에 직접 한 번 설정해줘야 했음(`maxPostSize`/`maxSwallowSize`를 150MB로 상향) — "코드는 다 맞는데 인프라 설정 때문에 안 되는" 케이스를 잡은 경험

> "배포는 로컬에서 GitHub에 push하고 Slack에 `/restart` 한 번 치는 것, 딱 두 가지 사람 개입만 남기고
> 나머지는 전부 자동화했습니다. 원래는 로컬에서 war를 직접 만들어서 별도 저장소에 올리는 방식이었는데,
> 지금은 서버가 소스를 받아서 직접 컴파일하고 war까지 만들도록 바꿨습니다. 컴파일이 실패하면 스크립트가
> 그 자리에서 멈추기 때문에 기존 서비스는 안 죽고, 성공이든 실패든 결과가 로그와 함께 Slack으로 바로
> 옵니다. 봇 권한도 특정 사용자·특정 채널에서만 실행되게 이중으로 제한해뒀습니다."

### 8-2. (p20, 슬라이드 10 상세) 상품등록 화면 — 2026-09-07 대폭 보강

이 화면은 슬라이드 한 장(View/Controller/DB 3줄)으로 요약하기엔 실제로 훨씬 복잡합니다. `vendor-product-write.jsp` 하나가 **1,400줄이 넘는 JS 로직**을 갖고 있고, 옵션 조합·이미지 미리보기·클라이언트 검증이 서로 맞물려 있어서, 발표에서 질문이 나올 만한 부분이 많습니다. 화면 구성 → 옵션 조합 로직 → 이미지 처리 → 제출 흐름 순서로 정리했습니다.

**전체 구조**: 폼 하나(`<form id="productForm" novalidate>`)에 6개 섹션이 세로로 쌓여 있습니다.

| 섹션 | 입력 항목 |
|---|---|
| 노출상품명 | 브랜드(또는 브랜드없음 체크), 노출상품명(100자 제한+글자수 카운터), 등록상품명(판매자 관리용) |
| 카테고리 | 검색어 자동완성 1개(8-1-2에서 다룬 `/category/getinfo?keyword=`) |
| 옵션 | 기본 상품가격 + "설정함/설정 안 함" 탭 + 옵션 그룹(최대 2개) → 조합 테이블 |
| 상품이미지 | 옵션별(또는 기본) 대표이미지 1장 + 추가이미지 최대 9장 |
| 상세설명 | 기본/옵션별 × 이미지업로드/에디터/HTML 3가지 작성방식 탭 + 모달 |
| 배송 | 출고지, 제주도서산간, 택배사, 배송방법, 묶음배송, 배송비종류, 출고소요일, 당일출고 |

`novalidate`를 붙여서 **브라우저 기본 검증을 끄고, 제출 버튼을 눌러도 실제로는 `<form>`의 기본 GET/POST가 아니라 JS가 `fetch()`로 가로채서 보냅니다** — 그래서 상단(`#topSubmitButton`)과 하단("판매요청") 두 버튼이 둘 다 같은 `submitProductForm` 함수를 호출하도록 되어 있습니다.

**① 옵션 그룹 → 조합 테이블 생성 (`cartesianCombine`)**
- "옵션 그룹"은 최대 2개까지만 추가 가능(`MAX_OPTION_GROUPS = 2`) — 이게 8-3/8-1-2에서 언급한 슬라이드의 "최대 2단계 옵션"의 실체입니다. `PRODUCT_OPTION`은 DB상 OPTION1~3, 3단계까지 컬럼이 있지만, **실제 등록 화면 UI는 2단계까지만 입력받도록 제한**되어 있어서 `option3`은 항상 비어있는 채로 서버에 전송됩니다
- 각 그룹(예: "사이즈")에 값을 하나씩 입력하면 "칩(chip)"으로 쌓이고(`renderChips`), 이 두 그룹의 값 목록을 **데카르트 곱(cartesian product)**으로 조합해서 옵션 테이블 행을 만듭니다 — 예: 사이즈[S,M,L] × 색상[블랙,화이트] = 6개 조합이 자동으로 6행 생성
- "옵션 설정 안 함" 탭을 고르면, 실제로는 조합을 만드는 대신 **"단일 상품" 가짜 조합 1개짜리 배열**을 만들어서 그대로 같은 테이블/이미지 렌더링 함수를 재사용합니다 — 옵션 있는 상품과 없는 상품을 화면 로직에서 분기 없이 하나로 처리하려는 의도
- 옵션 테이블(가격/재고 입력)과 이미지 테이블(대표/추가 이미지)이 **완전히 별개의 DOM 테이블인데, 같은 `combinations` 배열의 인덱스(`data-row`)로 서로 짝지어져 있습니다** — 그래서 옵션을 추가/삭제하면 두 테이블이 같이 다시 그려짐(`renderOptionTable()` 안에서 `renderImageTable()`을 같이 호출)

**② 이미지 업로드 — 서버 전송 전 클라이언트 미리보기**
- 이미지를 선택하면 즉시 서버에 안 올리고, `URL.createObjectURL(file)`로 **브라우저 메모리 안에서만 미리보기 URL을 만들어서** 화면에 보여줍니다(진짜 업로드는 최종 "판매요청" 시점에 한 번에 일어남). 이미지를 빼거나 다시 고를 때는 `URL.revokeObjectURL()`로 메모리를 명시적으로 해제 — 안 하면 브라우저 메모리 누수 가능성
- 파일 검증(`isValidImageFile`)을 **클라이언트에서 먼저** 하고(JPG/PNG만, 10MB 이하) 서버(`@MultipartConfig(maxFileSize=10MB)`)에서 다시 한 번 걸러서 이중 방어
- 체크박스로 여러 옵션 행을 고른 뒤 "대표이미지 일괄등록" 버튼으로 한 번에 같은 이미지를 여러 옵션에 적용하는 것도 가능(`getCheckedImageRows` + 일괄등록 버튼)

**③ 클라이언트 검증(`validateProductForm`) — 서버 검증과 이중 방어**
- 필수값(상품명/등록상품명/브랜드/카테고리/기본가/출고지) 외에, 옵션별로 **"기본가 + 옵션 판매가(가감액)를 더한 최종가가 0원 이하면 안 됨"**, **"모든 옵션에 대표이미지 필수"**까지 행 단위로 검사
- 여기서 걸러지는 항목 대부분은 `VendorProductWriteServlet`(8-1-2 참고)에서도 다시 검사합니다 — 클라이언트 검증은 사용자 경험(즉시 알림)을 위한 것이고, 서버 검증이 실제 방어선이라는 걸 명확히 구분해서 설명하면 좋습니다(클라이언트 검증은 개발자도구로 우회 가능하니까)

**④ 제출 — `buildProductFormData` → `fetch(POST)`**
- 옵션 개수만큼 `option_0_xxx`, `option_1_xxx` ... 식으로 **인덱스가 붙은 파라미터 이름을 동적으로 만들어서** 하나의 `FormData`에 다 담습니다(이미지 파일도 같은 방식으로 `option_i_mainImage`, `option_i_extraImage_j`) — 서버(`VendorProductWriteServlet.buildOptionDTO`)는 반대로 `optionCount`만큼 반복하면서 `"option_" + i + "_..."` 이름으로 다시 꺼내 씀. **이 인덱스 네이밍 규칙이 클라이언트·서버 사이의 암묵적 계약**이라, 둘 중 하나만 바뀌면 조용히 깨질 수 있는 부분(발표에서 "왜 JSON 대신 이런 방식을 썼나" 질문 나오면: 이미지 파일이 섞여 있어서 `multipart/form-data`가 필요했고, 그래서 JSON 대신 `FormData`+인덱스 네이밍을 택했다고 답하면 됨)
- 제출 중에는 두 제출 버튼을 `disabled` 처리해서 중복 클릭으로 같은 상품이 두 번 등록되는 걸 방지, 성공하면 상품번호를 안내하고 상품 목록(`/vendor/product`)으로 이동, 실패하면 서버가 내려준 에러 메시지를 그대로 alert

> "상품 등록 화면은 겉보기엔 폼 하나지만, 안에서는 옵션 그룹 2개의 값들을 조합해서 옵션 테이블을
> 자동으로 만들고, 그 옵션 개수만큼 이미지 업로드 슬롯도 같이 만들어지는 구조입니다. 옵션이 없는
> 상품도 '단일 상품'이라는 가짜 옵션 하나로 처리해서 로직을 하나로 통일했고요. 제출할 때는 이미지
> 파일이 섞여 있어서 JSON이 아니라 FormData로, 옵션 개수만큼 인덱스가 붙은 필드명을 만들어서
> 한 번에 전송합니다. 클라이언트에서 먼저 검증하지만 서버에서 다시 한 번 검증해서 이중으로
> 막아뒀습니다."

> 과제입니다."

### 8-4. (p22) GoodPang CI/CD 서버 자동 배포 흐름도 (Slack & Systemd)

> "Slack에 `/restart` 한 번 치면 서버까지 최신 소스가 자동으로 빌드·배포되는 구조입니다."

5단계 플로우:

1. **소스 수정 & Push** — Eclipse/IntelliJ에서 개발 → `git push origin main` → `sist_coupang_2026.git`
2. **Slack 명령 입력** — `/restart` 입력, Slack 멤버 ID로 권한 확인, 지정된 채널에서만 동작, 초기 응답으로 "서버 재시작 시작..." 표시
3. **Slack Bot 수신** — `slack_restart_bot.py` 데몬이 systemd(`slack-restart-bot`)로 상시 실행, Socket Mode(아웃바운드 웹소켓)라 공인 IP/포트포워딩 불필요, `subprocess.run('/root/restart.sh')` 호출
4. **서버 자동 빌드 & 배포** — ① Git Pull ② `javac` 빌드(WEB-INF/lib + Tomcat lib 참조) ③ `jar cf GoodPang.war`로 WAR 패키징 ④ Tomcat shutdown → 기존 ROOT.war 교체 → startup
5. **결과 알림 & 처리** — 성공/실패 여부를 git log·stdout/stderr와 함께 Slack 채널로 응답, 컴파일 실패 시 Tomcat 안 내리고 서비스 유지

하단 3개 상세 포인트:

- **[보안] Slack Socket Mode**: 아웃바운드 웹소켓만 사용, 공인 IP·포트포워딩·방화벽 개방 불필요, `ALLOWED_SLACK_USER_IDS`로 실행 권한 제한, 지정된 채널·허용된 관리자만 `/restart` 가능
- **[안정성] 컴파일 & 롤백 메커니즘**: `restart.sh`에 `set -e` 적용 → `javac` 컴파일 중 에러 발생 시 즉시 스크립트 중단, Tomcat shutdown 이전 단계에서 검증해서 서비스 장애 방지, 컴파일 성공 시에만 Tomcat 중지 & ROOT.war 교체
- **[빌드] 서버 자급자족 빌드**: Maven 표준 웹 구조(`src/main/java`, `webapp`), 의존성 라이브러리는 `WEB-INF/lib` 내장으로 독립 컴파일, `javac -cp "src/main/webapp/WEB-INF/lib/*:..."` 단독 수행, `jar cf GoodPang.war`로 서버에서 직접 패키징(Eclipse Export 불필요)

### 8-5. (p23, 슬라이드 12) 트러블슈팅

**① 승인 대기 상품 노출 버그**
- Problem: 관리자 승인을 안 받은("승인 대기") 상품이 카테고리 목록은 물론, 상품 상세페이지에 직접 URL로 접근해도 그대로 조회·구매가 가능했음
- Solution: 조회 경로가 카테고리 목록(`CategoryProductDAO`)과 상품 상세(`ProductDAO`) 두 군데로 나뉘어 있어서, 두 쿼리 모두에 `SALE_STATUS != '승인 대기' AND DISPLAY_YN = 'Y'` 조건을 각각 추가해서 막음

**② 상품명 길이 초과 오류**
- Problem: 상품 등록 시 등록상품명 컬럼이 `VARCHAR2(100)`(바이트 단위)였는데, 한글은 글자당 3바이트라 33자만 넘어도 `ORA-12899`(값이 너무 큼) 오류로 등록 실패
- Solution: `VARCHAR2(150 CHAR)`로 변경하여 문제 해결

**③ 대시보드 날짜선택 미반영 버그**
- Problem: 판매자 대시보드 상단에 날짜 선택 UI가 있었지만, 어떤 날짜를 골라도 항상 오늘 날짜 기준 데이터만 나오는 오류
- Solution: 일간·주간·월간 집계 쿼리 전부 `SYSDATE` 하드코딩을 없애고 선택한 날짜(`targetDate`)를 파라미터로 받도록 수정, 서블릿도 선택된 날짜를 파싱해 DAO로 넘기게 변경
