## 1. 프로젝트 컨셉 제안 (3가지)

### 컨셉 A. 개인용 인터넷뱅킹 (표준형)
일반 개인 고객이 사용하는 인터넷뱅킹을 그대로 축소한 형태. 회원가입, 계좌개설, 입출금, 이체, 거래내역, 예적금 가입까지 "은행다움"을 가장 직관적으로 보여줄 수 있는 컨셉.

### 컨셉 B. 개인+관리자 통합형 인터넷뱅킹 (관리자 콘솔 강화형)
컨셉 A의 기능에 더해 **은행 직원(관리자) 콘솔**의 비중을 크게 높인 형태. 고객 승인, 계좌 동결/해제, 이상거래 모니터링, 상품 등록/관리 등 운영자 관점 기능을 강화하여 백오피스 시스템까지 경험.

### 컨셉 C. 테마형 인터넷뱅킹 (특화 상품 중심형)
> ⚠️ **"컨셉 C(테마형 인터넷뱅킹)"는 실제 은행업계에서 쓰이는 공식 명칭이나 표준 분류가 아니라, 이 기획서에서 편의상 붙인 카테고리명**입니다. 다만 아래 개별 기능들은 실제 서비스에서 찾아볼 수 있는 것들을 참고했습니다 (예: 카카오뱅크의 "26주 적금", 토스뱅크의 "목표통장" → 적금 챌린지형 / 토스·뱅크샐러드의 소비 자동분류·리포트 기능 → 가계부 연동형 / 증권사 MTS·토스증권의 모의투자 기능 → 모의투자 연동형).

기본 뱅킹 기능 위에 하나의 특화 테마를 얹는 형태. 예를 들어:
- **적금 챌린지형**: 목표 저축, 자동이체 적금, 만기 시뮬레이션 등 적금 상품에 특화
- **가계부 연동형**: 이체/출금 내역을 자동으로 분류하여 소비 리포트를 제공하는 자산관리 기능 결합
- **모의투자 연동형**: 입출금 계좌에서 가상의 예수금으로 모의 투자(펀드 매수/매도)까지 확장

## 2. 컨셉별 주요 사용자(User Persona)

| 컨셉 | 주요 사용자 | 설명 |
|---|---|---|
| A. 표준형 | 일반 회원(개인 고객) | 계좌를 개설하고 입출금·이체·예적금을 이용하는 일반 사용자 |
| | 관리자(은행 직원) | 최소한의 운영 관리만 수행 |
| B. 관리자 강화형 | 일반 회원 + 은행 창구 직원(관리자) | 관리자가 고객 승인/계좌 상태 관리/이상거래 확인 등 실제 업무처럼 개입 |
| C. 테마형 | 일반 회원(재테크·저축에 관심 있는 고객) | 특정 목적(저축, 가계부, 투자)을 가진 사용자에 맞춘 부가기능 이용 |
| | 관리자 | 상품(적금/펀드) 등록 및 관리 |

## 3. 컨셉별 핵심 기능

### 컨셉 A. 표준형
- 회원가입 / 로그인 (본인인증 흉내: 휴대폰 인증 mock, 보안카드/OTP mock)
- 계좌 개설 (입출금 통장, 예금, 적금)
- 입금 / 출금
- 계좌이체 (본인 계좌 간, 타행/타인 계좌 이체)
- 거래내역 조회 (검색, 기간별 필터, 엑셀/CSV 내보내기)
- 예금 / 적금 가입 및 만기 처리
- 체크카드 신청/관리 (mock)
- 관리자: 회원/계좌 조회, 상품 관리

### 컨셉 B. 관리자 강화형
- 컨셉 A 전체 기능
- 관리자 승인 프로세스 (회원가입 승인, 계좌 개설 승인)
- 계좌 동결/해제, 이체 한도 설정
- 이상거래 탐지 룰(예: 단시간 고액 이체) 및 알림
- 관리자 대시보드 (전체 회원수, 거래량, 상품 가입 현황 통계)
- **[확장] 대출 신청/심사**: 재직정보 등 간단 조건 입력 → 조건 기반 자동 승인/거절 → 상환 스케줄 자동 생성
- **[확장] 실시간 알림**: 입출금/이체/대출 승인 발생 시 WebSocket 기반으로 화면에 즉시 알림 표시 (선택 구현, 어려우면 폴링 방식으로 대체)

### 컨셉 C. 테마형 (예: 적금 챌린지형)
- 컨셉 A의 계좌/이체/거래내역 기본 기능
- 목표금액/목표기간 설정 적금
- 자동이체(정기 적립) 스케줄링 + 배치 처리
- 목표 달성률 시각화(차트)
- 만기 시뮬레이션(이자 계산기)

## 4. 구현 난이도 구분

### 구현하기 좋은 기능 (난이도 낮음~중간, 학습효과 높음)
| 기능 | 비고 |
|---|---|
| 회원가입/로그인 | Spring Security + 세션 또는 JWT 학습에 적합 |
| 계좌 개설/조회 | 기본 CRUD + 계좌번호 생성 규칙 정도로 구현 가능 |
| 입금/출금 | 잔액 검증 로직으로 트랜잭션 처리 학습 |
| 계좌이체 | **동시성 제어(비관적 락 등) 학습 포인트**로 매우 좋음 |
| 거래내역 조회 | 페이징, 검색, 정렬 등 JPA/MyBatis 쿼리 실습에 적합 |
| 예적금 가입 | 상품 마스터 테이블 + 가입 테이블 구조 설계 연습 |
| 관리자 기본 기능(회원/계좌 조회, 상태 변경) | 권한 분리(Role) 학습에 적합 |
| 마이페이지(비밀번호 변경, 회원정보 수정) | 기본기지만 필수 |
| 대출 신청/상환 스케줄 계산 | 심사 로직을 단순 조건문(재직정보/희망금액 기준)으로 제한하면 난이도 적정, 상환 스케줄 계산 로직 학습에 좋음 |

### 구현 난이도가 높은 기능 (선택적으로만 도전)
| 기능 | 비고 |
|---|---|
| 실시간 이상거래 탐지 | 규칙 엔진 수준으로 간소화 필요 |
| 적금 자동이체 배치 스케줄러 | Spring Scheduler로 간소화하면 도전 가능 |
| OTP/생체인증 등 실제 보안 인증 연동 | mock으로 대체 권장 |
| 실시간 환율/타행 연동 | 외부 API 연동은 mock 데이터로 대체 |
| 대규모 동시성/부하 처리 | 학원 프로젝트 범위를 벗어남, 개념만 반영 |
| 모의투자/펀드 매매 로직 | 컨셉 C 선택 시 범위를 최소화해서 구현 |
| 실시간 알림(WebSocket/STOMP) | 새로운 기술 스택 학습이 필요하므로 핵심 기능 완료 후 여유 있을 때 도전. 시간이 부족하면 주기적 폴링(setInterval) 방식으로 대체 |

### 구현하지 않아도 되는 기능 (명확히 제외)
- 실제 금융결제원/오픈뱅킹 연동, 실제 계좌 실명 인증
- 실제 문자(SMS)/공동인증서/생체인증 연동 (전부 mock 처리)
- 실시간 대량 트랜잭션 처리, 장애 복구(HA), 다중 서버 분산 처리
- 외화 환전, 대출 심사, 보험 상품 등 뱅킹 외 금융업무
- PG사 연동 실제 결제

## 5. 최종 추천 컨셉: **컨셉 B (개인+관리자 통합형 인터넷뱅킹, 단 관리자 기능은 "적정 수준"으로 조정)**

### 추천 이유

**A안(순수 개인용)만으로는 4명이 나눠 맡기엔 업무량이 부족**합니다. 회원가입/로그인, 계좌, 이체, 거래내역, 예적금이 전부인데 이걸 4명이 나누면 한 사람당 파트가 너무 얇아져서 "각자 CRUD 화면 하나씩 만드는" 프로젝트로 전락하기 쉽습니다. 반대로 **C안(테마형)은 특화 기능(자동이체 배치, 모의투자 등)의 구현 난이도가 높아 일정 리스크가 크고**, 팀원 전원이 Spring Boot의 핵심(트랜잭션, 인증/인가, REST API 설계)을 고르게 경험하기보다 특정 파트에 난이도가 쏠릴 위험이 있습니다.

**B안**은 다음 이유로 4인 팀에 가장 적합합니다.

1. **업무 분담이 자연스럽게 4갈래로 나뉨**: (1) 인증/회원 (2) 계좌/입출금/이체 (3) 거래내역/예적금/카드 (4) 관리자 콘솔. 각 파트가 독립적인 도메인이면서도 서로 API로 연결되어 협업 경험을 쌓을 수 있습니다.
2. **은행 프로젝트다움이 확실히 드러남**: 단순 회원-게시판 CRUD가 아니라, "승인 프로세스", "계좌 상태(정상/동결)", "이체 한도" 같은 은행 도메인 특유의 상태(state)와 업무 로직이 들어가 포트폴리오에서 차별화됩니다.
3. **관리자 파트가 난이도를 스스로 조절 가능**: 이상거래 탐지 같은 고난도 기능은 "간단한 룰 기반"으로 낮추고, 승인/동결/통계 같은 실현 가능한 기능에 집중하면 일정 부담 없이 "규모 있어 보이는" 결과물을 만들 수 있습니다.
4. **보안/금융 특성을 자연스럽게 반영**: 관리자 승인 절차, 권한 분리(Role: USER/ADMIN), 계좌 동결 등은 실제 금융 서비스가 왜 이런 프로세스를 갖는지 이해하며 구현할 수 있어 학습효과가 큽니다.

즉, B안은 **"기능 개수"가 아니라 "도메인 상태와 업무 프로세스"로 프로젝트 규모를 키우는 방식**이라 학원 프로젝트 난이도를 벗어나지 않으면서도 포트폴리오 임팩트를 확보할 수 있습니다.

### 5-1. 기능 확장: 대출 + 실시간 알림

기본 뱅킹 기능(입출금/이체/예적금)만으로는 4명이 나눠 맡기에 파트가 얇다는 판단에 따라, 다음 두 가지를 **확장 기능**으로 추가합니다.

- **대출 도메인 추가**: 재직정보/희망금액 등 간단한 조건 입력 후 자동으로 승인/거절되는 대출 신청, 승인 시 상환 스케줄(원리금균등상환 등) 자동 생성. 새로운 도메인이 하나 늘어나 업무 분담에 여유가 생기고, 관리자 파트와도 자연스럽게 연결됩니다.
- **실시간 알림(WebSocket)**: 입출금/이체/대출 승인 시 화면에 즉시 알림이 뜨는 기능. 새로운 기술 스택(WebSocket/STOMP)을 경험할 수 있어 포트폴리오 임팩트가 크지만, 난이도가 있으므로 **선택 구현(스트레치 목표)**으로 분류합니다.

두 기능 모두 핵심 기능(회원/계좌/이체/예적금/관리자)이 안정적으로 완성된 이후에 시간이 허락하는 범위에서 진행하는 것을 원칙으로 합니다. 자세한 우선순위는 [6장](#6-기능별-구현-범위-제안)과 [14장 일정](#14-개발-순서-주차별-로드맵-총-7주-기준)을 참고하세요.

## 6. 기능별 구현 범위 제안

| 기능 영역 | 구현 범위 | 우선순위 |
|---|---|---|
| **회원가입** | 이메일/아이디, 비밀번호(암호화 저장), 이름, 휴대폰번호(형식 검증만), 생년월일. 이메일 인증은 **콘솔/로그 출력으로 mock** 처리하거나 실제 메일 발송(선택) | 핵심 |
| **로그인** | Spring Security 기반 세션 로그인 (또는 JWT). 로그인 실패 5회 시 잠금 등 기본 보안 정책 1~2개 반영. 아이디/비밀번호 찾기(본인인증 mock) | 핵심(찾기 기능은 심화) |
| **계좌** | 계좌 개설(입출금/예금/적금), 계좌 목록 조회, 계좌 상세(잔액, 상태), 계좌 해지. 계좌번호는 규칙 기반 자동 생성 | 핵심 |
| **계좌 심화** | 계좌 별명 설정, 자주 쓰는 계좌·받는사람 즐겨찾기 등록/관리 | 심화 |
| **입출금** | 입금/출금 처리, 잔액 부족 시 예외 처리, 트랜잭션 처리(원자성 보장) | 핵심 |
| **이체** | 본인/타인 계좌 이체, 1일 이체한도 검증, 이체 시 **동시성 제어(비관적 락 또는 낙관적 락)** 적용 | 핵심 |
| **이체 심화** | 예약이체(지정일 1회성), 정기(자동)이체(Spring Scheduler로 매월 반복 실행) | 심화(정기이체는 선택) |
| **거래내역** | 계좌별 거래내역 조회, 기간/유형별 검색, 페이징 처리 | 핵심 |
| **자산관리** *(신규)* | 카테고리별 소비 분석 차트, 거래내역 엑셀 다운로드, 목표저축 챌린지, 월별 자산 추이 그래프 | 심화(챌린지·추이 그래프는 선택) |
| **예금·적금** | 상품 목록 조회, 가입, 만기일 계산, 해지 시 이자 계산(단리 기준으로 단순화) | 핵심 |
| **카드** | 카드 신청(mock), 카드 목록 조회, 카드 상태(정상/정지) 변경. **실제 카드 결제 로직은 구현하지 않음** | 핵심 |
| **카드 심화** | 카드 사용내역(mock 가맹점 데이터) 조회, 한도 변경 신청 | 심화(한도변경은 선택) |
| **대출** *(확장)* | 대출 이자 시뮬레이터, 재직정보/희망금액 등 간단 조건 입력 → 조건 기반 자동 승인/거절 → 승인 시 상환 스케줄(원리금균등 등) 자동 생성/조회, 중도상환 신청. **신용평가/담보심사는 구현하지 않음** | 핵심(확장 도메인, 중도상환은 선택) |
| **고객센터** *(신규)* | 공지사항 조회, FAQ, 1:1 문의 등록/조회 및 관리자 답변 | 심화 |
| **알림** *(확장)* | 알림 목록/이력 조회, 알림 수신 설정(유형별 on/off), 실시간 알림(WebSocket)은 입출금/이체/대출 승인 시 화면에 즉시 표시. 어려우면 폴링 방식으로 대체 | 이력조회는 심화, 실시간(WebSocket)은 선택(스트레치) |
| **마이페이지/보안** | 회원정보 조회/수정, 비밀번호 변경, 회원탈퇴, 로그인 이력 조회, 접속 기기 관리 | 핵심(이력/기기관리는 심화·선택) |
| **관리자** | 회원 목록/승인, 계좌 상태 관리(동결/해제), 상품(예적금) 등록/수정, 대출 심사 관리, 대시보드 통계(회원수, 거래량, 대출현황 등) | 핵심 |
| **관리자 심화** | 카드 관리, 공지사항 관리, 1:1 문의 답변 관리, 관리자 활동 로그 조회, 이상거래 모니터링 | 심화(모니터링은 선택) |

> 이 표의 우선순위는 [8장 메뉴 구조](#8-전체-메뉴-구조)의 `[핵심]/[심화]/[선택]` 표기와 1:1로 대응합니다.

## 7. 실제 금융 서비스 vs 학원 프로젝트 구현의 차이

| 구분 | 실제 금융 서비스 | 이번 프로젝트 |
|---|---|---|
| 본인 인증 | 공동인증서, 생체인증, 본인확인기관 연동 | 아이디/비밀번호 + mock 인증(형식 검증 수준) |
| 계좌 개설 | 실명확인, 금융결제원 계좌 실명조회 | DB 내에서 규칙 기반으로 즉시 생성 |
| 보안 | HSM, 이상금융거래탐지시스템(FDS), 암호화 통신 인프라 | 비밀번호 암호화(BCrypt), HTTPS 흉내, 간단한 룰 기반 이상거래 체크 |
| 트랜잭션 | 분산 원장, 장애 복구, 이중화 서버 | 단일 서버 + DB 트랜잭션(ACID)만으로 정합성 보장 |
| 이체망 | 금융결제원 타행 이체망 연동 | 가상의 "타행"도 동일 DB 내 계좌로 처리(연동 없이 mock) |
| 카드 | VAN/PG사 실 결제 연동 | 카드 정보 관리(CRUD) 수준까지만 |
| 대출 | 신용평가시스템(CB사 연동), 등급별 금리 차등, 담보/보증 심사 | 재직정보/희망금액 등 단순 조건으로 즉시 승인·거절, 단일 고정금리 상품 |
| 법적 규제 | 전자금융거래법 등 각종 컴플라이언스 | 규제 준수는 다루지 않고 **개념만 문서화**(발표 시 "실무에서는 이런 규제가 있다" 정도로 언급) |

> 포인트: **UX와 도메인 로직(상태, 프로세스)은 실제와 유사하게, 인프라/외부연동/규제는 전부 mock 또는 생략**하는 것이 이 프로젝트의 원칙입니다.

## 8. 전체 메뉴 구조

팀원 4명 모두 개발 경험이 있는 점을 고려해, 기존 뼈대(회원/계좌/이체/예적금/카드/관리자)에 **이체 심화(예약·정기이체, 즐겨찾기), 자산관리, 고객센터, 마이페이지 보안설정**을 추가로 반영했습니다. 실제 구현 시 우선순위를 바로 판단할 수 있도록 각 항목에 등급을 표기합니다.

> **표기 기준**
> - `[핵심]` — 반드시 구현 (이게 없으면 "은행 서비스"라 부르기 어려운 기능)
> - `[심화]` — 난이도가 낮은 편이라 우수한 팀이면 기본 포함을 권장하는 기능
> - `[선택]` — 기술적으로 도전적이라 시간이 허락할 때만 진행하는 스트레치 기능

```
1. 메인 (비로그인 랜딩 페이지)
   1.1 서비스 소개 [핵심]
   1.2 로그인 / 회원가입 이동 [핵심]

2. 인증
   2.1 회원가입 (약관 동의 포함) [핵심]
   2.2 로그인 / 로그아웃 [핵심]
   2.3 아이디 찾기 [심화]
   2.4 비밀번호 재설정 (본인인증 mock) [심화]

3. 대시보드 (로그인 후 메인 홈)
   3.1 전체 자산 요약 (계좌+예적금+대출 통합, 자산 비중 차트) [심화]
   3.2 최근 거래내역 미리보기 [핵심]
   3.3 안 읽은 알림 미리보기 [선택]
   3.4 자주 쓰는 메뉴 바로가기 (이체/조회 단축) [심화]

4. 계좌
   4.1 계좌 개설 [핵심]
   4.2 계좌 목록 조회 [핵심]
   4.3 계좌 상세 (잔액/상태/최근거래) [핵심]
   4.4 계좌 별명 설정 [심화]
   4.5 자주 쓰는 계좌 즐겨찾기 관리 [심화]
   4.6 계좌 해지 [심화]

5. 입출금 / 이체
   5.1 입금 [핵심]
   5.2 출금 [핵심]
   5.3 일반 이체 (본인/타인 계좌) [핵심]
   5.4 예약이체 (지정일 1회성 이체) [심화]
   5.5 정기(자동)이체 (매월 특정일 반복 이체) [선택]
   5.6 이체 받는사람 즐겨찾기 관리 [심화]
   5.7 이체한도 조회 [핵심]
   5.8 이체 결과/영수증 확인 [핵심]

6. 거래내역
   6.1 전체 거래내역 조회 (검색/필터/페이징) [핵심]
   6.2 거래내역 상세 [핵심]
   6.3 카테고리별 소비 분석 (자동 분류 + 수동 수정) [심화]
   6.4 거래내역 엑셀(CSV) 다운로드 [심화]

7. 자산관리 [신규 메뉴]
   7.1 월별 소비 리포트 (카테고리별 차트) [심화]
   7.2 목표저축 챌린지 (적금 연계 목표금액/달성률) [선택]
   7.3 월별 총자산 추이 그래프 [선택]

8. 예금·적금
   8.1 상품 목록 조회 (기본금리/우대조건 비교) [핵심]
   8.2 상품 상세 [핵심]
   8.3 상품 가입 [핵심]
   8.4 내 예적금 현황 (만기일, 예상이자) [핵심]
   8.5 만기 알림 설정 [선택]
   8.6 중도 해지 (중도해지 이율 적용) [심화]

9. 카드
   9.1 카드 신청 [핵심]
   9.2 내 카드 목록 [핵심]
   9.3 카드 상세 (사용내역 조회, mock) [심화]
   9.4 카드 상태 관리 (정지/재발급) [핵심]
   9.5 카드 한도 변경 신청 [선택]

10. 대출
    10.1 대출 이자 시뮬레이터 (가입 전 계산기) [심화]
    10.2 대출 신청 [핵심(확장 도메인)]
    10.3 심사 결과 조회 [핵심(확장 도메인)]
    10.4 내 대출 현황 / 상환 스케줄 조회 [핵심(확장 도메인)]
    10.5 중도상환 신청 [선택]

11. 알림
    11.1 실시간 알림 (헤더 벨 아이콘) [선택]
    11.2 알림 목록/이력 조회 [심화]
    11.3 알림 수신 설정 (유형별 on/off) [선택]

12. 고객센터 [신규 메뉴]
    12.1 공지사항 목록/상세 [심화]
    12.2 FAQ [심화]
    12.3 1:1 문의 등록/내 문의 조회 [심화]

13. 마이페이지
    13.1 회원정보 조회/수정 [핵심]
    13.2 비밀번호 변경 [핵심]
    13.3 보안설정 - 로그인 이력 조회 [심화]
    13.4 보안설정 - 접속 기기 관리 [선택]
    13.5 보안설정 - 이체한도 변경 신청 [심화]
    13.6 회원 탈퇴 [핵심]

14. 관리자 (ADMIN 권한 전용)
    14.1 관리자 대시보드 (통계 차트: 회원/거래/상품/대출) [핵심]
    14.2 회원 관리 (목록, 승인/거절, 상태변경) [핵심]
    14.3 계좌 관리 (목록, 동결/해제, 이체한도 변경 승인) [핵심]
    14.4 상품 관리 (예적금 상품 등록/수정) [핵심]
    14.5 대출 심사 관리 [핵심(확장 도메인)]
    14.6 카드 관리 (발급 현황, 정지 처리) [심화]
    14.7 공지사항 관리 (등록/수정/삭제) [심화]
    14.8 1:1 문의 답변 관리 [심화]
    14.9 거래 모니터링 (이상거래 후보 목록) [선택]
    14.10 관리자 활동 로그 조회 [심화]
```

기존 12개 메뉴(회원/계좌/이체/거래내역/예적금/카드/대출/알림/마이페이지/관리자)에 **자산관리(7번)**, **고객센터(12번)** 2개 메뉴가 새로 추가되어 총 14개 최상위 메뉴, 하위 항목 기준 약 50개로 늘어났습니다. 우선순위(`[핵심]/[심화]/[선택]`)는 [6장](#6-기능별-구현-범위-제안)의 우선순위와 연결되며, 4주차까지 `[핵심]`을 완성하고 5~6주차에 `[심화]`→`[선택]` 순으로 채워가는 것을 권장합니다.

## 11. 테이블 간 관계 설명 (ERD 설계 전 이해용)

- **MEMBER : ACCOUNT = 1 : N**
  한 회원은 여러 계좌(입출금/예금/적금)를 가질 수 있음. `ACCOUNT.MEMBER_ID`가 `MEMBER`를 참조.

- **ACCOUNT : TRANSACTION_HISTORY = 1 : N**
  한 계좌에서 여러 건의 거래(입금/출금/이체)가 발생. `TRANSACTION_HISTORY.ACCOUNT_ID`가 `ACCOUNT`를 참조.

- **ACCOUNT : TRANSFER = 1 : N (양방향 참조)**
  이체는 출금계좌(`FROM_ACCOUNT_ID`)와 입금계좌(`TO_ACCOUNT_ID`) 두 개의 `ACCOUNT`를 참조. 하나의 `TRANSFER` 건은 출금 계좌/입금 계좌 양쪽에 각각 `TRANSACTION_HISTORY` 레코드를 1건씩 생성(더블 엔트리 방식 권장).

- **PRODUCT : PRODUCT_SUBSCRIPTION = 1 : N**
  하나의 예적금 상품에 여러 회원이 가입. `PRODUCT_SUBSCRIPTION`은 `MEMBER_ID`, `PRODUCT_ID`, `ACCOUNT_ID`를 모두 참조하는 교차 테이블 성격.

- **MEMBER : CARD = 1 : N**
  한 회원이 여러 장의 카드를 가질 수 있고, 카드는 특정 `ACCOUNT`(결제 연동 계좌)를 참조.

- **MEMBER : ADMIN_LOG = 1 : N**
  관리자(=MEMBER 중 ROLE이 ADMIN인 회원)가 수행한 작업 이력을 기록. `ADMIN_LOG.ADMIN_ID`가 `MEMBER`를 참조.

- **MEMBER : FAVORITE_ACCOUNT = 1 : N** *(신규)*
  회원 한 명이 여러 개의 즐겨찾기 계좌(자주 쓰는 이체 대상)를 등록. `FAVORITE_ACCOUNT.MEMBER_ID`가 `MEMBER`를 참조.

- **TRANSACTION_CATEGORY : TRANSACTION_HISTORY = 1 : N** *(신규)*
  거래내역 한 건은 하나의 소비 카테고리에 속함(미분류 허용). 자산관리 메뉴의 카테고리별 리포트 집계에 사용.

- **MEMBER : SCHEDULED_TRANSFER = 1 : N** *(신규)*
  회원이 등록한 예약/정기이체 목록. `SCHEDULED_TRANSFER.FROM_ACCOUNT_ID`가 `ACCOUNT`를 참조하며, 배치(Scheduler)가 주기적으로 조회해 실행 후 `TRANSFER`/`TRANSACTION_HISTORY`를 생성.

- **PRODUCT_SUBSCRIPTION : SAVING_GOAL = 1 : 1** *(신규)*
  적금 가입 건 하나에 목표저축 챌린지 정보가 1건 연결(선택 가입).

- **CARD : CARD_USAGE_HISTORY = 1 : N** *(신규)*
  카드 한 장에 여러 건의 사용내역(mock)이 기록됨.

- **MEMBER : NOTIFICATION_SETTING = 1 : N** *(신규)*
  회원별로 알림 유형(입출금/이체/대출/공지 등)마다 수신 여부를 설정.

- **MEMBER(ADMIN) : NOTICE = 1 : N** *(신규)*
  관리자가 작성한 공지사항 목록. `NOTICE.ADMIN_ID`가 `MEMBER`(ROLE=ADMIN)를 참조.

- **MEMBER : INQUIRY = 1 : N, MEMBER(ADMIN) : INQUIRY = 1 : N** *(신규)*
  회원이 작성한 1:1 문의(`INQUIRY.MEMBER_ID`)와 답변한 관리자(`INQUIRY.ANSWERED_ADMIN_ID`, nullable)를 각각 참조하는 이중 FK 구조.

- **MEMBER : LOGIN_LOG = 1 : N** *(신규 필수화)*
  회원의 로그인 시도 이력을 기록. 마이페이지 보안설정 화면(13.3)에서 본인 이력 조회.

- **MEMBER : LOAN = 1 : N** *(확장)*
  한 회원이 여러 건의 대출을 신청할 수 있음. `LOAN.MEMBER_ID`가 `MEMBER`를 참조.

- **LOAN : LOAN_REPAYMENT_SCHEDULE = 1 : N** *(확장)*
  승인된 대출 1건에 대해 회차별 상환 스케줄이 여러 건 생성됨. `LOAN_REPAYMENT_SCHEDULE.LOAN_ID`가 `LOAN`을 참조.

- **MEMBER : NOTIFICATION = 1 : N** *(확장)*
  회원 한 명에게 여러 건의 알림이 발생. `NOTIFICATION.MEMBER_ID`가 `MEMBER`를 참조하며, 입출금/이체(`TRANSACTION_HISTORY`)나 대출 승인(`LOAN`) 이벤트 발생 시점에 생성되는 파생 데이터 성격.

- **MEMBER.ROLE**
  단일 `MEMBER` 테이블에서 `ROLE` 컬럼(USER/ADMIN)으로 권한을 구분하는 방식을 권장(테이블을 분리하지 않아 단순함 유지).

> 설계 원칙: 모든 금액/잔액 변경은 **반드시 `TRANSACTION_HISTORY`에 기록을 남긴 뒤** `ACCOUNT.BALANCE`를 갱신하는 순서로 구현하여, 실제 은행 시스템처럼 "거래 원장 우선" 원칙을 학습 목적으로 반영합니다.

## 12. 4인 팀 업무 분담 제안

메뉴가 14개로 늘어난 만큼, 담당 메뉴 번호까지 명시해 각자의 범위를 명확히 했습니다.

| 파트 | 담당 메뉴 | 담당 영역 | 주요 산출물(테이블) |
|---|---|---|---|
| **팀원 1 — 인증/보안/대시보드 파트** | 2, 3, 13 | 회원가입, 로그인/로그아웃, 아이디/비번찾기, Spring Security 설정, 대시보드(자산요약), 마이페이지, 보안설정(로그인이력/접속기기) | `MEMBER`, `LOGIN_LOG`, 인증/인가 공통 모듈(다른 파트가 재사용) |
| **팀원 2 — 계좌/이체/자산관리 파트** | 4, 5, 6, 7 | 계좌 개설/즐겨찾기, 입출금, 일반·예약·정기이체, 동시성 제어, 거래내역/소비분석, 자산관리 리포트 | `ACCOUNT`, `FAVORITE_ACCOUNT`, `TRANSACTION_HISTORY`, `TRANSACTION_CATEGORY`, `TRANSFER`, `SCHEDULED_TRANSFER`, `SAVING_GOAL` (프로젝트의 핵심 로직) |
| **팀원 3 — 예적금/카드/대출 파트** | 8, 9, 10 | 예적금 상품 가입/해지, 카드 신청·관리, **대출 신청/심사/상환 스케줄 (확장)**, 대출 이자 시뮬레이터 | `PRODUCT`, `PRODUCT_SUBSCRIPTION`, `CARD`, `CARD_USAGE_HISTORY`, `LOAN`, `LOAN_REPAYMENT_SCHEDULE` |
| **팀원 4 — 관리자/고객센터/공통 인프라 파트** | 11, 12, 14 | 관리자 대시보드/회원·계좌·상품·대출심사·카드 관리, 공지사항/FAQ/1:1문의(고객센터), **실시간 알림 인프라(확장)**, 공통 레이아웃, 예외처리/공통 응답 포맷 | `ADMIN_LOG`, `NOTICE`, `FAQ`, `INQUIRY`, `NOTIFICATION`, `NOTIFICATION_SETTING`, 공통 인프라(Exception Handler, Response DTO, WebSocket 설정, 프론트 공통 레이아웃) |

**분담 원칙**
- 팀원 1이 만드는 인증/권한 모듈은 **1주차에 최우선으로 완료**하여 나머지 팀원이 로그인 사용자 정보(세션/토큰)를 바로 활용할 수 있게 함.
- 팀원 2의 계좌/이체 로직이 프로젝트의 기술적 난이도 핵심이므로, 예약·정기이체·자산관리 같은 `[심화]/[선택]` 항목은 가장 나중에 착수.
- 공통 코드(응답 DTO, 예외 처리, 유틸)는 팀원 4가 **1주차에 먼저 세팅**하여 전원이 동일한 컨벤션으로 개발하도록 함.
- 프론트엔드(화면)는 각자 자기 도메인 화면을 직접 만들되, 공통 레이아웃/CSS는 팀원 4가 초기 템플릿을 제공.
- **대출(팀원3)과 실시간 알림(팀원4)은 확장 도메인**, **예약·정기이체(팀원2)·자산관리(팀원2)·고객센터(팀원4)·보안설정(팀원1)은 심화 메뉴**이므로 각 파트가 자기 영역의 `[핵심]`을 먼저 끝낸 뒤 `[심화]→[선택]` 순으로 진행.
- 4개 파트 모두 "필수 도메인 1~2개 + 심화 메뉴 1~2개"로 구성되어 있어, 팀원 간 업무량이 한쪽으로 쏠리지 않도록 균형을 맞췄습니다.
- 알림은 팀원2(계좌/이체)·팀원3(대출)이 발생시키는 이벤트를 팀원4가 구독해 전송하는 방식으로 협업 (예: 이체 완료 시점에 이벤트를 발행하면 팀원4의 알림 모듈이 이를 받아 `NOTIFICATION`을 생성).

## 13. GitHub 충돌 최소화 개발 방식

1. **브랜치 전략**: `main`(배포 가능 상태 유지) → `develop`(통합 브랜치) → 기능별 `feature/{파트명}-{기능명}` 브랜치. 각자 자기 브랜치에서 작업 후 `develop`으로 PR.
2. **패키지 구조로 물리적 충돌 최소화**: 도메인별 패키지(`member`, `account`, `product`, `admin`)를 처음부터 분리하여 각자 다른 파일/디렉토리에서 작업하도록 설계. 공통 파일(설정, 공통 응답 클래스)은 최소 인원(1명)만 수정 권한을 갖도록 규칙화.
3. **PR 리뷰 필수화**: `develop` 브랜치에 직접 push 금지, 최소 1명 이상 리뷰 후 머지.
4. **잦은 커밋 & 작은 단위 PR**: 기능 단위로 작게 쪼개 자주 머지하여 충돌 범위를 줄임.

6. **이슈/칸반 보드 연동**: GitHub Issues + Projects(칸반)로 작업 항목을 트래킹하여 중복 작업 방지.

## 14. 개발 순서 (주차별 로드맵, 총 7주 기준)

| 주차 | 목표 | 세부 내용 |
|---|---|---|
| **1주차** | 기획 확정 + 환경 세팅 | 요구사항 확정, ERD 설계, 와이어프레임, 프로젝트 초기 세팅(Spring Boot 프로젝트 생성, Git 저장소/브랜치 전략 확정, DB 스키마 생성), 공통 모듈(응답 DTO, 예외처리) 구축 |
| **2주차** | 인증 + 계좌 기본 기능 | 회원가입/로그인(Spring Security), 계좌 개설/조회 API 및 화면 구현. 각 파트 도메인 Entity/Repository 골격 작성 |
| **3주차** | 입출금/이체 핵심 로직 | 입금/출금, 계좌이체(동시성 제어 포함), 거래내역 기록 로직 구현 및 테스트 |
| **4주차** | 예적금/카드/거래내역 조회 (`[핵심]` 마무리) | 예적금 상품 가입, 만기 계산, 카드 관리, 거래내역 검색/페이징 구현. **여기까지가 전 파트 `[핵심]` 완료 목표 시점** |
| **5주차** | 관리자 기능 + 심화 메뉴 착수 | 관리자 대시보드/회원/계좌/상품/대출심사 관리(`[핵심]`) 구현. 파트별로 `[핵심]`이 끝난 팀원부터 순서대로 심화 메뉴 착수: 팀원1(보안설정), 팀원2(즐겨찾기·예약이체·소비분석), 팀원3(대출·카드 심화), 팀원4(고객센터·알림) |
| **6주차** | 심화·선택 메뉴 마무리 + 통합 | 각 파트 `[심화]` 항목 마무리, 여유되는 팀원은 `[선택]`(정기이체, 실시간 알림, 목표저축 챌린지, 거래 모니터링 등) 도전. 전체 기능 통합 및 화면 스타일 정리 |
| **7주차** | 테스트 + 버그픽스 + 발표 준비 | 통합 테스트, 예외 케이스 점검, 시나리오 리허설, 발표자료(PPT) 및 시연 시나리오 작성 |

> 메뉴가 확장된 만큼 일정도 6주 → **7주**로 한 주 늘리는 것을 권장합니다. 일정이 더 짧다면 `[선택]` 항목 전체와 `[심화]` 항목 일부(정기이체, 카드 한도변경, 접속기기 관리 등)부터 제외하고, `[핵심]`과 `[심화]` 중 발표 임팩트가 큰 항목(보안설정, 소비분석, 대출)을 우선 남기는 순서로 축소하세요.

## 15. 최종 발표용 추천 기능 및 시연 시나리오

### 발표에서 강조하기 좋은 포인트
- **동시성 제어가 적용된 계좌이체**: "왜 은행 시스템에서 동시성 제어가 중요한가"를 설명하며 Lock 적용 전/후 비교 시연
- **거래 원장 기반 잔액 관리**: `TRANSACTION_HISTORY`를 근거로 잔액이 계산되는 구조 설명 (신뢰성 있는 설계임을 어필)
- **관리자 승인 프로세스**: 회원가입 → 관리자 승인 → 계좌 개설 가능이라는 실제 은행 업무 플로우 재현
- **REST API 기반 설계**: 화면(View)과 API(백엔드)가 분리된 구조로 설계했음을 강조 (Postman/Swagger로 API 문서화해서 보여주면 가산점)
- **자산관리 리포트**: 거래내역이 자동으로 카테고리 분류되어 소비 차트로 시각화되는 모습은 발표에서 시각적 임팩트가 큼
- **대출 심사 자동화 + 상환 스케줄 계산**: 단순 CRUD가 아니라 "조건 → 판정 → 후속 데이터 생성"이라는 업무 로직을 보여줌

### 시연 시나리오 (예시 흐름)
1. 신규 회원가입 → (관리자 계정으로 전환) 관리자가 회원 승인
2. 로그인 → 입출금 계좌 개설 → 계좌 별명 설정
3. 입금 → 잔액 반영 확인
4. 즐겨찾기에 등록한 계좌로 이체 → 양쪽 계좌 거래내역에 반영되는 것 확인
5. **(심화) 예약이체 등록** → 지정한 시각에 자동 실행되는 것을 배치 로그로 확인
6. 적금 상품 가입 → 만기일/예상이자 확인, 목표저축 챌린지 진행률 확인
7. 거래내역 화면에서 기간별 검색/필터링 + **(심화) 카테고리별 소비 분석 차트** 시연
8. **(확장) 대출 이자 시뮬레이터**로 예상 상환액 확인 → 대출 신청 → 조건 입력 후 자동 승인 결과 확인 → 상환 스케줄 조회
9. **(선택) 실시간 알림**: 다른 브라우저(또는 다른 계정)에서 내 계좌로 이체 발생 시, 알림이 화면에 즉시 표시되는 모습 시연
10. **(심화) 고객센터**에서 1:1 문의 등록 → 관리자 계정에서 답변 처리
11. 관리자 계정으로 전환 → 대시보드에서 전체 회원수/거래량/대출 현황 통계 확인, 특정 계좌 동결 처리 시연
12. (동결된 계좌로) 이체 시도 시 정상적으로 차단되는 예외 처리 시연

> 11~12번 시나리오처럼 **정상 케이스뿐 아니라 예외/제약 조건이 의도대로 동작하는 것**을 보여주면 "단순 CRUD가 아니라 업무 로직을 이해하고 구현했다"는 인상을 강하게 줄 수 있습니다. `[심화]/[선택]` 표시가 붙은 단계(5, 7 후반부, 8~10)는 실제로 구현된 항목만 포함하고, 구현하지 못했다면 시나리오에서 자연스럽게 제외하면 됩니다.
